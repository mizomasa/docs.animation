AIエージェント設計の型カタログ

AIエージェントの
デザインパターン集

パターンとは、「エージェントの頭の動かし方の型」です。新しい技術の名前ではなく、タスクの進め方・品質の上げ方・振り分け方の、再利用できる設計の単位です。

出発点は、推論してツールを呼び、結果を見て次を考える単純なループ（ReAct）。このページは、そのループだけでは足りなくなったときに「足す部品」として4つのパターンを、アニメーションで解説します。

考える→ ツールを実行→ 結果を観察→ また考える…
読み方：まず全体マップで「どの層のパターンか」を掴み、次に4本のアニメーションで動きを追ってください。すでに別ページで扱った連携パターン（司令塔型・ハンドオフ・パイプライン）や土台（RAG・メモリ）は、マップでの位置づけのみに留めています。

MAP

パターン全体マップ

パターンは3つの層に分かれます。1つのエージェントの頭の動かし方（単体）、複数エージェントの組み方（連携）、そしてそれらを支える土台です。今回アニメーションで深掘りするのは、色枠の4つです。

単体パターン ― 1体の頭の動かし方

  • ReAct推論→実行→観察の基本ループ。すべての土台
  • Plan-and-Execute今回先に計画を立て、計画どおりに実行する
  • Reflection今回自分の出力を自分で批判し、直す
  • Evaluator-Optimizer今回生成役と評価役を分け、合格まで回す

連携パターン ― 複数体の組み方

  • 司令塔型（Orchestrator-Workers）司令塔が分解し、作業役が並行実行
  • ハンドオフ担当が別の専門エージェントへ引き継ぐ
  • パイプライン工程が固定の直列処理。各段を型で縛る
  • Router今回入力を見て処理先を振り分ける

土台 ― パターンを支える部品

  • ツール / MCP外部操作の手段と、その標準インターフェース
  • RAG検索で根拠を集めてから生成する
  • メモリ短期（会話内）・長期（永続化）の記憶
  • 構造化出力出力をスキーマで縛り、機械処理可能にする
  • 上限・ガードレールループ回数・コストの上限と、入出力の検証層
P
PLAN-AND-EXECUTE

Plan-and-Execute ― 先に計画、後で実行

題材：市場調査レポートの作成。ReActが「一歩ずつ考えながら進む」のに対し、こちらは最初に全体の計画を立ててから、計画に沿って実行します。

要点計画（Planner）と実行（Executor）を分離するのが肝です。そして計画は絶対視しない ― 途中で想定外が起きたら、計画そのものを書き換える「リプランニング」を挟みます。

📋 タスク

「ある製品分野の市場調査レポートを作成して」
納期：本日中 ／ 形式：比較表つき

🧭 Planner（計画役）

全体を見て手順を設計する。実行はしない

⚠ 想定外

必要な市場規模データが見つからない

🗂 計画ボード

市場規模・成長率のデータを集める
主要プレイヤーを比較表にまとめる
市場規模の数字を根拠に本文を執筆する公開事例と推定の断り書きつきで本文を執筆する
代替データ（公開事例・統計の二次資料）を補完収集する
全体を通読し、レポートとして仕上げる

🔧 Executor（実行役）

計画の項目を上から順にこなす

📄 レポート

未着手

向いている用途

  • 手順が多い長めのタスク（調査、レポート、移行作業）
  • 途中の進捗を人間が見て確認したい仕事
  • 実行前に計画レビューを挟みたい場面

向いていない場面

  • 数ステップで終わる短いタスク（計画の手間が勝つ）
  • 進めながらでないと方針が決まらない探索的な仕事

コスト感

中

計画立案と、場合により再計画の分だけ呼び出しが増える。ただし無駄な試行錯誤が減るため、長いタスクでは総量が下がることも多い。

R
REFLECTION / SELF-CRITIQUE

Reflection ― 自分の出力を自分で批判する

題材：案内文の下書き作成。生成した直後に「批判する視点」に切り替えて自分の出力を点検し、直してから出す、という一往復のパターンです。

要点生成と批判を同じエージェントが担います。分業はしません。その代わり「書き手のつもり」から「読み手・校正者のつもり」へ視点を切り替える指示が効きどころです。
🤖 エージェントは1体だけ ― 生成役と批判役を、同じエージェントが帽子を替えて担います

✍ 下書き v1

「当施設は来月リニューアルオープンします。営業時間は9時から17時までです。ぜひお越しください。」
…一見ふつう。でも点検すると問題が3つ

✍ 書き直し v2

「当施設は4月1日にリニューアルオープンします。営業時間は9時〜17時（最終入館16時30分）です。休館日は毎週火曜です。皆さまのお越しをお待ちしています。」

✅ 改善版を出力

問題点3件すべてに対応済み

🔍 批判フェーズ ― チェック観点

事実の誤りはないか 抜けている情報はないか トーンは適切か
✗「来月」が曖昧 ― 具体的な日付がない（事実・明確さ）
✗最終入館時刻と休館日が抜けている（抜け）
✗結びが事務的で、案内文として冷たい（トーン）
→修正指示1：日付を「4月1日」と明記する
→修正指示2：最終入館16時30分・火曜休館を追記する
→修正指示3：結びを歓迎の表現に変える

向いている用途

  • 文章・コードなど「下書きの質」を1段上げたい生成タスク
  • 評価基準を細かく固定しなくてもよい場面
  • 手軽に導入したい品質改善（構成が最小）

向いていない場面

  • 自分では気づけない種類の誤りが多い領域（同じ盲点を共有する）
  • 合否を厳密に判定しなければならない場面

コスト感

低〜中

生成1回＋批判・修正で、おおむね呼び出し2〜3回分。1体で完結するため構成コストは最小です。

E
EVALUATOR-OPTIMIZER

Evaluator-Optimizer ― 評価役を分けて合格まで回す

題材：仕様書に沿ったコード生成。生成役（Optimizer）とは別の評価役（Evaluator）が、あらかじめ固定された評価基準で採点し、合格するまで差し戻します。

Reflectionとの違い①評価役が別エージェントで、自分の盲点を共有しない　②評価基準（ルーブリック）が事前に固定され、ブレない　③合否判定が明示的で、ループに回数上限を設ける。

🛠 生成役（Optimizer）

仕様書：「入力チェックつきのユーザー登録関数を作る」

成果物 v1

登録関数は完成。ただしメール形式チェックがなく、エラー時の戻り値が仕様と違う

成果物 v2（修正版）

NG項目2件を修正：形式チェックを追加し、エラー形式を仕様どおりに統一

✅ 合格 ― 出力

全項目クリアのため、この成果物を採用

📏 評価役（Evaluator）― 生成役とは別エージェント

固定のルーブリックで機械的に採点する

採点結果（1回目）

評価項目判定
必須項目：登録処理が動くOK
必須項目：メール形式チェックNG
形式：エラー戻り値の形式NG
禁止事項：平文でのパスワード保存OK

↩ 差し戻し

NG項目のリストを添えて生成役へ返却

再評価（2回目）

全項目 OK ― 合格

⛔ ループ回数の上限

合格しないまま上限（例：3回）に達したら、ループを止めて「最良の版を出す」「人間にエスカレーションする」など、必ず出口を用意します。無限ループはコスト事故のもとです。

向いている用途

  • 仕様・規約など、合否基準を言語化できる成果物（コード、定型文書、翻訳）
  • 品質を「なんとなく」ではなく基準で担保したい場面
  • テストや検証を自動化できる領域

向いていない場面

  • 評価基準そのものを作れない・曖昧なタスク
  • 1回で十分な品質が出る単純な生成（往復が無駄になる）

コスト感

中〜高

1往復ごとに生成＋評価の2回分。往復回数に比例して増えるため、上限設定とセットで導入します。

Rt
ROUTER / ROUTING

Router ― 入力を見て処理先を振り分ける

題材：社内問い合わせ対応。すべての入力を同じ相手に渡すのではなく、入り口で内容を判定し、難易度と種類に応じた処理先へ振り分けます。

要点狙いは「全部を高性能モデルで処理しない」こと。簡単な質問に高いコストを払わず、難しい相談には十分な能力を当てる ― コストと品質の配分を入り口で決めるパターンです。判定にはキーワード等のルール、軽量な分類モデル、LLMによる判定などを組み合わせます。
✉「パスワードのリセット方法は？」 ✉「新制度への移行計画を相談したい」 ✉「給与明細の金額が先月と違う」
🚦 Router ― 内容を判定して振り分け
キーワード・ルール 分類モデル LLMによる判定

⚡ 軽量モデル

定型・簡単な質問を即答
回答：「手順ページのリンク＋手順3行」で完了

🧠 高性能モデル

複雑な相談にじっくり対応
回答：現状整理と移行ステップ案を提示

👤 専門エージェント

給与・人事など専門領域専用（権限つき）
回答：明細を確認し、差異の理由を説明

振り分けの効果 ― もし全部を高性能モデルで処理したら

全件・高性能モデルコスト 100 ／ 遅い
Routerで振り分けコスト 約38 ／ 簡単な質問は高速に
※比率は説明用のイメージです。実際の削減幅は問い合わせの内訳によります。

向いている用途

  • 問い合わせ対応など、量が多く種類もばらばらな入力
  • 難易度の偏りが大きいワークロード（大半は簡単、少数が難しい）
  • 専門領域ごとに権限や知識を分けたい場面

向いていない場面

  • 入力の種類がほぼ均一（振り分ける意味がない）
  • 量が少なく、全件を高性能モデルで処理しても困らない規模
  • 誤振り分けのコストが極端に高い場面（判定精度の検証が先）

コスト感

導入後は下がる

判定処理の分だけ入り口で小さなコストが増えますが、大半の入力を軽量な処理に流せるため、全体では大きく下がるのが普通です。

COMPARE

比較表 ― 5パターンを並べる

基準のReActを含めた5つを、複雑さ・コスト・品質向上の効き方・失敗しやすい点で比較します。

パターン複雑さコスト品質向上の効き方失敗しやすい点
ReAct（基準）低 ― ループ1つ低〜中（歩数に比例）その場の試行錯誤で徐々に長いタスクで迷走・同じ失敗の繰り返し
Plan-and-Execute中 ― 計画役と実行役の分離中（計画＋再計画の分）全体の見通しと手順の抜け防止最初の計画が実態とずれると引きずる。再計画を省くと脆い
Reflection低 ― 1体に批判フェーズ追加低〜中（＋1〜2回）書きっぱなしの粗を一往復で除去自分の盲点は自分では見えない。改善が表面的になりがち
Evaluator-Optimizer中〜高 ― 2体＋基準設計中〜高（往復回数に比例）固定基準で合否を担保。ブレが小さい基準の設計ミスがそのまま品質の天井になる。上限なしだと無限ループ
Router中 ― 入り口に判定層全体では低下（配分の最適化）難しい入力に十分な能力を当てられる誤振り分け。難しい相談が軽量側に流れると品質事故になる
HOW TO CHOOSE

選び方 ― 足し算の順番

最初から全部入りを目指さず、困りごとが出た順に足していくのが実務的です。

1
まず ― すべての出発点

ReActで始める

単純なループ＋ツール＋構造化出力＋上限設定。これで解けるタスクは意外に多い。複雑なパターンは、ここで困ってから足します。

2
タスクが長く、手順が多いなら

＋ Plan-and-Execute

迷走や手順の抜けが出てきたら、計画と実行を分離。再計画の仕組みもセットで入れます。

3
出力の品質が要るなら

＋ Evaluator-Optimizer（手軽さ優先なら Reflection）

合否基準を言語化できるなら評価役を分けるEvaluator-Optimizerが本命。基準がまだ曖昧なら、まずReflectionで一往復させるだけでも効きます。

4
量と種類が増えてきたら

＋ Router

入力の種類が増え、コストや応答速度が課題になったら入り口に振り分けを置く。専門エージェントへの分岐もここで生まれます。

共通の土台：どのパターンを選んでも、ループ回数・コスト・時間の上限、実行トレースの記録、不可逆な操作の前の人間承認（Human-in-the-Loop）は別途必要です。パターンは「頭の動かし方」であり、安全装置はその外側に置きます。
GLOSSARY

用語解説

ReAct
推論（Reasoning）と行動（Acting）を交互に繰り返す基本ループ。考えてツールを呼び、結果を見てまた考える。
リプランニング（再計画）
実行中の想定外を受けて、残りの計画を立て直すこと。Plan-and-Executeの耐久性を決める要素。
ルーブリック
評価項目と判定基準を並べた採点表。Evaluator-Optimizerでは事前に固定し、評価のブレを抑える。
差し戻し
評価でNGとなった成果物を、NG項目の指摘つきで生成役へ返すこと。指摘の具体性が修正の質を決める。
ループ上限
生成⇔評価などの反復に設ける最大回数。上限到達時の出口（最良版の採用、人間へのエスカレーション）も併せて設計する。
振り分け（ルーティング）
入力の内容・難易度に応じて処理先（モデル、プロンプト、専門エージェント）を選ぶこと。判定にはルール、分類モデル、LLM判定を使う。
軽量モデル / 高性能モデル
高速・低コストだが能力は控えめなモデルと、低速・高コストだが難しい処理に強いモデルの対比。Routerの振り分け先の典型。
専門エージェント
特定領域の知識・ツール・権限だけを持つエージェント。Routerやハンドオフの受け先になる。
構造化出力
出力をJSONスキーマ等で縛り、プログラムから確実に処理できる形にすること。連携パターンの段と段をつなぐ前提になる。
Human-in-the-Loop
送信・削除・購入など不可逆な操作の前に、人間の承認を挟む設計。パターンの外側に置く安全装置。
AIエージェントのデザインパターン集 ― 例はすべて汎用的な題材で構成しています。各パターンは単独でも、組み合わせても使えます（例：Routerで振り分けた先でPlan-and-Executeを回し、成果物をEvaluator-Optimizerで検査する）。
