Agent SDKの仕組みアニメーション

Claude Agent SDK や OpenAI Agents SDK で作ったエージェントは、「モデルが考えて → ツールを呼んで → 結果を見て → また考える」というエージェントループで動きます。題材は一般的なタスク「READMEを読んで要約をファイルに書き出す」。9ステップの動きに、両SDKの実装コードのハイライトを連動させて追ってみましょう。

概要

Agent SDKは、LLMに「考えて、道具を使って、結果を見て、また考える」という繰り返し（エージェントループ）を、アプリケーションへ組み込むための開発キットです。

モデル単体では文章を返すことしかできず、ファイルを開いたりコマンドを実行したりといった現実の操作は担えないため、その実行役と進行役として生まれました。

ループの制御や履歴の管理、安全のためのブレーキといった周辺の面倒を引き受けるので、開発者はタスクの指示と道具の用意に集中できます。

背景

Agent SDKが生まれた背景 — 「考えるだけのモデル」に手を付ける

モデルは考えるだけで、手を持っていない

LLMのAPIは、入力された文章に対して文章を返す仕組みです。受け答えは賢くても、ファイルを開く、検索する、コマンドを実行するといった、コンピューター上の実際の操作はできません。モデルが返せるのは「この道具を、この引数で使いたい」という要求までで、それを実行する手は別に必要でした。

しかもエージェントの仕事は一往復では終わりません。道具を使った結果を見て次の手を決め、また道具を使う。その繰り返しの末にようやくタスクが完了します。この繰り返しを誰がどう回すのかが、エージェントを作ろうとしたときに最初にぶつかる問題でした。

「要求と実行の分離」自体は、モデルが道具を使う仕組みとしてAPIの側に用意されていました。ただし、それを受けて実行し、結果を返し、また送る、という往復の管理は、APIを使う側のプログラムの責任として残されていたのです。

ループの骨格は単純でも、付随する部品が多い

繰り返しの骨格自体は素直です。指示と道具の一覧と履歴をモデルに送り、返ってきた要求を実行し、結果を履歴に積んで送り直す。ただ、実際に運用しようとすると部品が次々に必要になります。モデルが最終回答を出すまで回し続ける終了判定、履歴が膨らんだときの圧縮や切り詰め、暴走を止める最大ターン数、危険な操作の前に許可を取る仕組み、道具が失敗したときの結果の返し方、コストの上限などです。

これらをアプリケーションごとに自作すると、同じような車輪を何度も作ることになります。安全弁の有無や作り込みの丁寧さにもばらつきが出て、品質は作り手任せになってしまいます。

ないとどうなるか

Agent SDKがなければ、エージェントを作るたびにループと安全弁を手作りすることになります。ブレーキを欠いたまま動かして、モデルが同じ操作を延々と繰り返すような事態を招いたり、逆に怖くて単発の質問応答しか任せられなかったりと、モデルの能力と実際に任せられる仕事の間に大きな溝が残ります。SDKは、その溝を埋める土台として用意されたものです。

もちろん、今でもループを自前で書くことはできます。ただ、まともに運用できる形に仕上げるまでの距離が、SDKの有無で大きく変わる、というのが実情です。言い換えるとSDKは、モデルの能力を引き出すための足場であり、足場の出来が、任せられる仕事の範囲をそのまま決めます。

ステップを進めると、そのステップで中心になる行がハイライトされます。タブを切り替えると、もう一方のSDKでも対応する行が光ります。書き方は違っても、やっていること（ループ）は同じです。

agent.ts — @anthropic-ai/claude-agent-sdk
agent.py — openai-agents

見比べポイント：Claude Agent SDKは Read / Edit / Bash などのツールがSDKに組み込みで、allowedTools で許可するだけ。OpenAI Agents SDKは @function_tool を付けた自分の関数をツールとして登録するのが基本形です。
読み物

仕組みを文章で読む — エージェントループの1周と、その先

アニメーションを再生しなくても流れが追えるよう、9ステップの内容を文章でもたどっておきます。

材料をそろえて、モデルへ送る

アプリがタスクを渡すところから始まります。SDKはモデルのAPIに、どう振る舞うかの指示、使えるツールの一覧（名前・説明・入力スキーマ）、これまでの会話履歴（messages）の3点をまとめて送ります。最初の時点では、履歴の中身はタスクそのものだけです。モデルが判断に使える情報は、この3点に限られます。

ツールの一覧には、道具ごとに「いつ使うべきか」まで含めた説明が付けられます。モデルは道具の実装の中身を見ているわけではなく、名前と説明とスキーマだけを頼りに選ぶため、この3点の書き方が、そのまま道具の使われ方を決めます。

モデルは判断だけを返し、実行はSDKが担う

題材のタスクでは、モデルは「まずREADMEを読む必要がある」と判断し、文章ではなく tool_use という構造化された要求を返します。ここでモデルはファイルを開いていません。要求を受け取ったSDKが、実際にファイルを読んで中身を取り出します。現実の世界の操作は、すべてSDKの動いているアプリ側の仕事です。

読み取った内容は tool_result として履歴に積まれ、SDKは履歴全体をモデルへ送り直します。モデル自身に前回の記憶はなく、履歴を毎回渡されることで「続き」から考えられるようになっています。

なお、道具の実行前に許可を取るかどうかも、この段階で効いてきます。読み取りのような安全な操作は自動で進め、書き込みやコマンド実行のような影響の大きい操作では人の確認を挟む、といった制御はSDK側の設定で行います。

繰り返しの先にある終了

モデルは積み上がった履歴を読み直し、次は要約をファイルへ書き出すよう tool_use で要求します。SDKが実行し、結果が返る。ステップの形は1周目とまったく同じで、この繰り返しがエージェントループの正体です。タスクが複雑なほど、周回数は増えていきます。

モデルが「もう道具は要らない」と判断すると、tool_use ではなく通常の文章で最終回答を返します。これがループの自然な終了で、SDKはその回答をアプリへ渡して処理を終えます。途中で最大ターン数などの上限を超えた場合は、エラーとして強制的に止まります。終わり方まで含めて設計されている点が、単にAPIを呼ぶだけのプログラムとの違いです。

この流れを眺めると、モデルが担っているのは判断だけで、状態の保持も実行もSDK側にあることが分かります。エージェントの「賢さ」はモデルの性能に、「確実に仕事を終わらせる力」はループを回す側の作りに、それぞれ依存しているのです。

補足 1

ループの終了条件と安全弁

  • 自然な終了：モデルが tool_use を返さず、文章（最終回答）を返したらループは終わります。「もうツールは不要」というモデル自身の判断が終了条件です。
  • 最大ターン数：無限ループや暴走を防ぐ安全弁。Claude Agent SDKは maxTurns、OpenAI Agents SDKは Runner.run(..., max_turns=...) で上限を決められます。超えるとエラーで止まります。
  • 権限・コストの上限：危険なツールの実行前に許可を求める設定や、トークン使用量の上限も、実運用では欠かせないブレーキです。
補足 2

コンテキスト（messages）の増え方と圧縮

モデルは「前回の応答」を覚えているわけではありません。毎ターン、SDKが履歴（messages）全体を送り直すことで、モデルは続きから考えられます。今回の例でも履歴はこう育ちます。

user：タスクassistant：tool_useuser：tool_resultassistant：tool_useuser：tool_resultassistant：最終回答
  • ツール結果が大きい（長いファイル、検索結果の山など）と、履歴は一気に膨らみます。モデルの読める上限（コンテキストウィンドウ）に近づくと、古い情報が扱えなくなります。
  • 対策の考え方：圧縮・要約（ここまでの履歴を短い要約に置き換えてから続ける）、結果の切り詰め（ツール結果の要点だけを履歴に残す）、タスクの分割（サブエージェント／ハンドオフで担当を分ける）などがあります。
  • コストも履歴の長さに比例します。「何周回るか」と「1周でどれだけ増えるか」が、エージェントの料金と速度をほぼ決めます。
補足 3

ツール定義の書き方 — モデルの判断材料

モデルはツールの中身（実装コード）は見ていません。見ているのは名前・説明・入力スキーマ（どんな引数を、どの型で渡すか）の3点だけです。だからこの3点の書き方が、そのまま「正しいツールを、正しい引数で呼べるか」を決めます。

{ "name": "read_file", "description": "指定したパスのファイルの内容を読み取る", "input_schema": { "type": "object", "properties": { "path": { "type": "string", "description": "読み取るファイルのパス" } }, "required": ["path"] } }
  • OpenAI Agents SDKでは、@function_tool を付けると関数の名前・docstring・型注釈からこの定義が自動生成されます。
  • Claude Agent SDKの組み込みツールは定義済みですが、自作ツールを足す場合も考え方は同じです。
  • 説明が曖昧だとモデルはツールを選び間違えます。「いつ使うべきか」まで説明に書くのがコツです。

強みと弱み

Agent SDKの良い点と弱点

良い点：回すための部品が揃った状態から始められる

終了判定、履歴の管理、最大ターン数、権限の確認といった「エージェントを安全に回すための部品」が最初から用意されています。開発者は、指示の書き方や道具の用意といった、そのエージェント固有の部分に時間を使えます。Claude Agent SDKとOpenAI Agents SDKのどちらもMCPに対応しているので、外部の道具を取り込む道も開かれています。

もう1つの利点は、モデルやSDKの進化に追随しやすいことです。ループの作法は各SDKが保守してくれるため、モデルが新しくなっても、アプリケーション側は指示と道具の見直しを中心に対応できます。

弱点：履歴の長さが、そのままコストと時間になる

ループが1周するたびに履歴は増え、次のモデルの呼び出しはその分だけ重くなります。周回数の多いタスクでは料金も待ち時間も膨らみやすく、履歴の圧縮や、道具の結果の切り詰めといった工夫が欠かせません。速さと安さは、ほぼ「何周回るか」と「1周でどれだけ増えるか」で決まります。

弱点：挙動はモデルの判断次第で、SDKごとの作法も違う

次にどの道具を使うかはモデルが決めるため、同じ指示でも毎回同じ動きになるとは限りません。また、組み込みツールを許可して使うSDKと、自分の関数を登録していくSDKとでは設計の作法が異なり、途中で乗り換える場合は書き直しのコストがかかります。

テストのしにくさも付きまといます。同じ入力で必ず同じ手順になるとは限らないため、通常のプログラムのような「入力に対する出力の一致」では検証できず、結果の妥当性を別の方法で確かめる工夫が要ります。

補足 5

用語解説

エージェントループ

「モデルが考える → ツールを呼ぶ → 結果を見る → また考える」を、モデルが最終回答を出すまで繰り返す仕組み。エージェントの心臓部。

tool_use（ツール使用）

モデルが返す「このツールを、この引数で呼んでほしい」という構造化された要求。モデル自身は実行せず、実行はSDK側の仕事。

tool_result（ツール結果）

SDKがツールを実行した結果。会話履歴（messages）に積まれてモデルに渡され、モデルはこれを見て次の判断をする。

ハンドオフ

OpenAI Agents SDKの仕組み。タスクの担当エージェントを別の専門エージェントに引き継ぐこと。Claude Agent SDKのサブエージェントに近い発想。

ガードレール

OpenAI Agents SDKの安全機構。入力・出力・ツール実行の前後に検証を挟み、不適切な内容や想定外の動作を止める。

コンテキスト

モデルが1回の判断で読める情報の全体（指示・ツール定義・会話履歴）。履歴が増えるほど1回の呼び出しが重く、高くなる。

まとめ

まとめ

Agent SDKは、考えることしかできないモデルの周りに、実行する手と、繰り返しを回す進行役と、止めるためのブレーキを用意する土台です。中心にあるのはエージェントループという単純な繰り返しで、SDKごとの違いは、その周辺の部品の揃え方や作法に表れます。道具の定義の書き方がモデルの判断材料になる点と、履歴の増え方がコストと速度を決める点は、どのSDKを選んでも共通する勘所です。この2点を押さえておくと、アニメーションの動きも、コードとの対応も読み解きやすくなります。
