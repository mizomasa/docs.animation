認証方式の体系整理

認証方式はかなり種類があります。ただ、整理するときに重要なのは、「何を使って本人を確認するのか」と「どのような仕組みで認証するのか」は別の話だということです。例えば、パスワード認証、パスキー認証、OAuth 2.0、SAML認証などは、同じ階層の概念ではありません。

軸1：「何を使って」本人を確認するのか

知識・所持・生体といった「認証要素」の話。パスワードや指紋はこちら側に属します。

軸2：「どのような仕組みで」認証するのか

認証の実装技術や、認証情報を他システムへ連携する方式の話。OAuth 2.0やSAMLはこちら側に属します。

この2つの軸を分けて考えることが、全体を理解する出発点です。以下、現在使われている認証方式を体系的に整理します。

CORE ― アーキテクチャ設計で整理しておきたいこと

階層モデル ― 用語を階層に分けると混乱しない

ここが一番重要です。認証に関する用語は、以下のように階層を分けて考えると混乱しません。

アニメーションA：5層の階層モデルに構成例を当てはめる
構成例 ― 認証要素：所持＋生体／認証方式：パスキー／プロトコル：WebAuthn／認証連携：OpenID Connect／セッション：Cookie／認可：RBAC
①認証要素知識・所持・生体例：所持＋生体
②認証方式・認証器パスワード・OTP・パスキー・証明書例：パスキー
③認証プロトコル・連携方式WebAuthn・Kerberos・OIDC・SAML・mTLS例：WebAuthn ＋ OIDC
④認証後のセッション・トークンCookie・Session ID・ID Token・Access Token例：Cookie
⑤認可（Authorization）RBAC・ABAC・ACL・スコープ例：RBAC

例えば上記の構成では、各層がそれぞれ別の役割を担っています。「パスキーで認証する」と言っても、要素・方式・プロトコル・セッション・認可はすべて別の話です。

SECTION 2

具体的な認証方式一覧

実際のシステム開発で登場する方式を一覧にします。

2-1パスワード・知識ベース認証

方式概要主な用途
パスワード認証IDとパスワードで確認Webサービス
PIN認証数字などの暗証番号ATM、端末

秘密の質問あらかじめ登録した回答アカウント復旧など

秘密の質問は、現在では単独の本人認証手段としては推奨しにくい方式です。

HOTPとTOTPの違い

2-3生体認証

方式概要主な用途
指紋認証指紋の特徴を照合スマホ、PC
顔認証顔の特徴を照合スマホ、入退室
虹彩認証虹彩パターンを照合高セキュリティ施設
静脈認証指・手の静脈パターンを照合銀行ATMなど
声紋認証声の特徴を照合コールセンター
コラム：生体情報はサーバーへ送られるとは限らない

注意したいのは、指紋認証やFace IDなどは、それ自体がサーバーに送信される認証情報とは限らないことです。

例えばパスキーでは、端末内で指紋や顔による本人確認を行い、その結果を利用して秘密鍵による署名を実行します。サーバーは公開鍵でその署名を検証します。

2-4公開鍵暗号方式・証明書認証

方式概要主な用途
公開鍵認証秘密鍵で署名し、公開鍵で検証SSH、FIDO2
クライアント証明書認証クライアント証明書で本人・端末を確認企業システム、金融
mTLSクライアントとサーバー双方が証明書で認証API、マイクロサービス
スマートカード認証ICカード内の秘密鍵などを利用社員認証、行政
PIV認証個人識別用の証明書・スマートカードを利用官公庁、企業

このあたりは、エンタープライズや金融機関のシステムで重要になります。

2-5パスワードレス認証

方式概要主な用途
パスキー公開鍵暗号を使ったパスワードレス認証Web・モバイル
FIDO2WebAuthnとCTAPを組み合わせた規格Web認証
Windows HelloPINや生体認証で端末内の認証情報を利用Windows
WebAuthnブラウザと認証器を連携するWeb標準APIWebサービス

特に重要なのがパスキーです。従来のパスワード認証と違い、サーバー側にパスワードを保存せず、公開鍵を登録しておきます。認証時には、サーバーからのチャレンジに対して端末内の秘密鍵で署名し、サーバーが公開鍵で検証します。フィッシング耐性があることも大きな特徴です。

2-6シングルサインオン・認証連携

ここは少し分類が違います。これらは、認証そのものというより、認証結果やユーザー情報を別のシステムに連携するための仕組みです。

方式・規格概要主な用途
SAML 2.0XMLベースの認証情報連携企業SSO
OpenID ConnectOAuth 2.0を拡張した認証プロトコルWeb・モバイルSSO
OAuth 2.0APIアクセス権限を委譲する仕組み外部API連携
Kerberosチケットを利用したネットワーク認証Active Directory
LDAPディレクトリサービスへのアクセスプロトコルユーザー情報管理・認証連携
OAuth 2.0 ― 認可の仕組み
「このアプリにAPIを利用させてよいか」

APIアクセス権限の委譲を扱います。ユーザーが誰かを確認する仕組みではありません。

VS
OpenID Connect ― 認証プロトコル
「このユーザーは誰なのか」

OAuth 2.0を拡張した認証プロトコルで、Web・モバイルのSSOに使われます。

混同しやすいポイント

OAuth 2.0単体は認証プロトコルではありません。「権限を委譲する仕組み」と「本人を確認する仕組み」は別の役割です。

2-7多要素認証（MFA）

MFAは特定の認証方式ではなく、異なる認証要素を組み合わせる考え方です。重要なのは、認証要素の数ではなく、異なる種類の要素を組み合わせることです。

アニメーションB：MFAの組み合わせ判定
要素の「種類」が同じか違うかに注目してください。色は要素の種類を表します。
知識情報 所持情報 生体情報
「次へ」または「再生」で、組み合わせ例を1つずつ判定していきます。
パスワードのみパスワード＝知識×要素は知識1つだけ。単一要素なのでMFAではありません。
パスワード＋PINパスワード＝知識PIN＝知識×2つ使っても、どちらも知識情報。種類が同じなのでMFAにはなりません。
パスワード＋SMS OTPパスワード＝知識SMS OTP＝所持○知識＋所持。異なる種類の組み合わせです。
パスワード＋指紋パスワード＝知識指紋＝生体○知識＋生体。異なる種類の組み合わせです。
セキュリティキー＋PINセキュリティキー＝所持PIN＝知識○所持＋知識。異なる種類の組み合わせです。
パスキー＋生体認証パスキー＝所持生体認証＝生体○所持＋生体による利用者確認。異なる種類の組み合わせです。

最近の企業システムや金融サービスで重要な考え方です。

IPアドレスや位置情報などは、それ単独で本人を証明する認証要素ではなく、リスク判断のための補助情報です。

2-9システム間・サービス間の認証（マシン認証）

ユーザーではなく、アプリケーションやサーバー同士が認証する方式です。

方式概要主な用途
API Key固定キーでアクセス元を識別API

クライアント証明書証明書でサービスを識別mTLS
JWT Bearer署名付きトークンで認証・情報伝達API
SSH公開鍵認証秘密鍵による署名で接続サーバー管理

最近はAIエージェントにも関係してくる領域です。例えば、AIエージェントがSharePointや社内APIにアクセスするとき、ユーザーのIDを引き継ぐのか、エージェント自身のIDでアクセスするのか、といった設計が必要になります。

SECTION 3

認証方式を比較する ― セキュリティと利便性

代表的な方式を、セキュリティと利便性の観点で比較します。

認証方式フィッシング耐性利便性主な課題
パスワード低い普通漏洩・使い回し
SMS OTP低い高いSIMスワップなど
Email OTP低い高いメールアカウント依存
TOTP低い普通コードの詐取
プッシュ認証方式による高い承認疲れ
指紋・顔＋パスキー高い高い端末・アカウント復旧
セキュリティキー高い普通紛失・管理
クライアント証明書高い普通証明書管理
mTLS高い低〜普通運用・証明書管理

※一般的な傾向です。実装や運用条件によって異なります。特に生体認証単体と、パスキーを生体認証で利用するケースは区別が必要です。

NISTの2025年版ガイドライン（SP 800-63-4）でも、フィッシング耐性を持つ暗号学的認証が重視されています。手入力するOTPは、フィッシング耐性のある認証には分類されません。

設計に直結する3つの問い

認証技術を学ぶなら、単に方式の名前を覚えるよりも、次の3つを理解するとアーキテクチャ設計に直結します。

問い 1 ― 人の認証

人間のユーザーをどう認証するか

問い 2 ― マシンの認証

システム・サービス・AIエージェントをどう認証するか

問い 3 ― 認可

認証した主体に何を許可するか（認可）

特にこれからは、ユーザー認証だけでなく、AIエージェントのアイデンティティ管理や委任認証も重要になってくると思います。
