Computer-Using Agent（CUA）の仕組み

CUA（Computer-Using Agent）は、AIが画面のスクリーンショットを見て、マウスとキーボードを人と同じように操作するエージェントです。 専用のAPIがない画面でも、ボタンや入力欄という「人と同じ入口」から入って作業できる——そこが本質です。申請フォームを入力して送信する例で、操作のループを8ステップで再生できます。

        SECTION 2
        
画面でこう見える — 「目」と「手」のループ

        
エージェントと画面のあいだで起きているのは、単純な往復の繰り返しです。スクリーンショットが「目」、マウスとキーボードが「手」、そのあいだでモデルが考えます。

      

      

        
📸 スクリーンショットを撮る（目＝知覚）
　→ 🧠 画面を読み、次の一手を考える（推論）
　　→ 🖱️ click / type / key を送る（手＝行動）
　　　→ 🖥️ 画面が変わる → またスクリーンショットへ（ループ）

        
ポイントは、エージェントが受け取るのが原則として画面の画像（ピクセル）だということです。Webページの裏側の構造（DOM）を直接読む方式とは違い、人間が見ているものとほぼ同じ情報から判断します。だからAPIのないデスクトップアプリや、画像として表示されるだけの画面でも操作できます。

      

      

        

          
ピクセルを見る方式 スクリーンショット

          
画面を画像としてモデルに渡し、ボタンの位置を座標で特定します。どんなアプリでも同じやり方で扱えるのが強みです。一方で、小さい文字の読み取りや、似たボタンの見分けはモデルの視覚能力に依存し、座標がずれると誤クリックになります。

        

        

          
アクセシビリティツリー併用 構造も読む

          
OSやブラウザが持つ「画面要素の構造情報」（アクセシビリティツリー）を画像と併せて渡す方式です。要素の名前や役割がテキストで分かるため、位置の特定が安定しやすくなります。ただし構造情報を持たないアプリでは使えず、画像だけの方式と使い分け・併用されます。

        

      


      
      

        SECTION 3
        
実際の中身のフロー — 4つの構成要素

        
CUAの実装は、大きく4つの部品に分かれます。「考えるモデル」だけでは動かず、操作する環境と、安全を担保する層がセットで必要です。

      

      

        

          
① モデル

          
スクリーンショットを理解する視覚能力と、タスクを手順に分解する推論能力を兼ねたモデルです。画面要素の位置を座標で言い当てる「グラウンディング」の精度が、成否を大きく左右します。

        

        

          
② 実行環境

          
エージェントが操作するコンピュータそのものです。クラウド上の仮想マシン（VM）、ブラウザ専用環境、あるいは自分のPC上で動かす形があります。使い捨てできるVMなら、失敗しても環境ごと捨てられます。

        

        

          
③ アクション実行層

          
モデルが出した指示（click(x, y)、type、key、スクロールなど）を、OSやブラウザへの実際の入力イベントに変換する層です。スクリーンショットの取得もここが担います。

        

        

          
④ 安全層

          
危険な操作を止めるための仕組みです。重要な操作の前で人の確認を挟む、画面内の不審な指示を検知する分類器、外部と切り離したサンドボックスなどが含まれます（詳しくはセクション5）。

        

      

      

        SECTION 3
        
主な担い手の年表

        
「モデルが画面を操作する」という発想が、研究デモから製品・基盤へ広がってきた流れです。

      

      

        

          2024年10月
          
Anthropic「computer use」

          
Claudeがスクリーンショットを見てデスクトップを操作する機能を、公開ベータとして発表しました。開発者がAPI経由で「AIに画面操作させる」形が広く知られるきっかけになったとされます。

        

        

          2025年1月
          
OpenAI「CUA」モデルと Operator

          
OpenAIは画面操作専用のモデルを「CUA（computer-using agent）」と名付け、それを使った Operator を発表しました。のちに、この機能はChatGPTのエージェント機能へ統合されたと報告されています。

        

        

          2025年〜
          
Google Gemini の computer use

          
GoogleもGemini系モデルに画面操作の能力を持たせ、ブラウザ操作を中心に提供を広げています。主要なモデル提供者がそろってこの領域に入った形です。

        

        

          オープンソース基盤
          
trycua/cua と CUA Agent Kit

          
trycua/cua は、エージェント用の仮想デスクトップ環境（LumeによるVMなど）を提供するオープンソース基盤です。CVS Healthが公開した CUA Agent Kit は発想が逆で、「探索はAIにやらせるが、繰り返し実行はコード化して行う」というハイブリッド方式を採ります（セクション4参照）。

        

      


      
      

        SECTION 4
        
RPAとの違い

        
画面操作の自動化といえば従来は RPA（Robotic Process Automation） でした。どちらも「画面を操作する」点は同じですが、次の一手の決め方が根本的に違います。

      

      

        

          
            
観点RPACUA

          
          
            

              次の一手の決め方
              事前に固定。人間が手順をシナリオとして書き、機械はそれを再生する
              その場で判断。モデルが画面を見て、次に何をするかを毎回推論する
            

            

              画面変更への耐性
              弱い。ボタンの位置や文言が変わると、シナリオがそのまま止まることが多い
              強い。レイアウトが多少変わっても、画面を見て新しい位置を探せる
            

            

              再現性・決定性
              決定的。同じ入力なら毎回まったく同じ動きをする
              非決定的。実行ごとに経路が少しずつ変わりうる
            

            

              速度とコスト
              速く安い。再生だけなので計算資源はわずか
              遅く高い傾向。ステップごとにモデルの呼び出し（画像入力を含む）が発生する
            

            

              失敗の仕方
              止まる。想定外では例外になって停止するので、被害は限定的
              静かに間違える。想定外でも「それらしい操作」を続けてしまい、誤ったまま完了扱いになることがある
            

            

              作る速さ
              遅い。対象画面ごとにシナリオの設計・調整が要る
              速い。タスクを文章で頼むだけで、未知の画面でも試行を始められる
            

          
        

      

      

        ベンチマークの読み方： PC操作の代表的なベンチマーク OSWorld では、初期のエージェントの成功率は14.9%にとどまり、OpenAIのCUAでは38.1%、人間のベースラインは約72%と報告されています。改良版の OSWorld-Verified では上位モデルが人間超えを達成したとの報告もある一方、長時間の実務ワークフローを測る OSWorld 2.0 では最良のエージェントでも5割弱にとどまるとされます。「1回解ける」ことと「毎回解ける」ことは別物で、短い課題の成功率を、そのまま実務の信頼性と読み替えないことが大切です。
      

      

        

          
使い分けの原則 — 優先順位

          
① API があれば API を使う
② コネクタ／MCP など構造化された接続
③ 手順が固定なら RPA
④ CUA は「他に手段がない画面」の切り札

          
画面操作は、構造化された接続が使えないときの最終手段と考えるのが基本です。画面は変わりやすく、検証もしにくいため、上位の手段が使えるならそちらを優先します。

        

        

          
ハイブリッド — 探索はAI、繰り返しはコード

          
両者のいいとこ取りが、AIに手順を探索させて成功した操作をコード化し、繰り返しはそのコードで実行する方式です（CVS Healthの CUA Agent Kit がこの発想とされます）。探索の柔軟さと、再生の速さ・再現性を両立でき、画面が変わったときだけAIに直させます。

        

      


      
      

        SECTION 5
        
リスクと対策

        
「画面を見て何でも操作できる」ことは、そのまま「画面に映るものすべてが攻撃や事故の入口になる」ことでもあります。代表的なリスクと、実装側で用意される対策です。

      

      

        

          
① 画面内プロンプトインジェクション

          
Webページや画像、文書の中に「この指示に従え」という文言を埋め込み、画面を読んだエージェントを釣る攻撃です。CUAでは画面そのものが攻撃面になり、タスクと無関係な指示がスクリーンショット経由で入り込みます。

        

        

          
② 誤操作とサイレントな失敗

          
似たボタンの押し間違いや、値の入力ミスに気づかないまま進む失敗です。「保存はできたが金額が違う」のように、成功したつもりで間違っている状態が最も厄介で、完了判定を画面の見た目だけに頼ると見逃します。

        

        

          
③ 認証情報・画面の丸見え

          
スクリーンショットには、その瞬間に表示されているすべての情報が写ります。パスワード入力欄や個人情報を含む画面が、モデルの入力やログにそのまま残るおそれがあり、情報の取り扱い範囲が広がります。

        

        

          
④ 取り消せない操作

          
送信、支払い、削除といった操作は、一度実行すると元に戻せません。人間の作業なら手が止まる場面でも、エージェントは確認なしに実行できてしまうため、影響の大きい操作ほど歯止めが必要です。

        

        

          
⑤ 再現性とコスト

          
毎ステップでLLMを呼び出すため、長いタスクほど時間と費用がかさみます。また実行ごとに経路が変わりうるので、「昨日できた操作が今日は違う動きをする」ことがあり、監査や再現テストが難しくなります。

        

        

          
対策の基本セット

          
専用のVM／サンドボックスで動かし、権限は最小限に。アクセス先ドメインは許可リストで絞る。送信・支払いなど重要な操作の前では人の確認（テイクオーバー）を挟む。操作ログとスクリーンショットを監査証跡として残す。そして、いきなり本番ではなく低リスクなタスクから始めるのが定石です。

        

      

      

        要点： CUAの安全はモデルの賢さだけでは決まりません。「どの環境で・どの権限で・どこまで人を確認に挟むか」という運用設計が、そのまま安全性になります。
      


      
      

        GLOSSARY
        
用語解説

      

      

        

          
グラウンディングgrounding

          
「送信ボタンを押して」という言語的な指示を、画面上の具体的な座標（x, y）に対応づけること。CUAのモデルに求められる中核能力で、ここがずれると誤クリックになります。

        

        

          
知覚―推論―行動ループperception–reasoning–action loop

          
スクリーンショットで画面を知覚し、次の一手を推論し、クリックや入力として行動し、変わった画面をまた知覚する、というCUAの基本の繰り返し構造です。

        

        

          
OSWorldベンチマーク

          
実在のOSやアプリ上での課題（ファイル操作、アプリの設定変更など）で、PC操作エージェントの成功率を測る代表的なベンチマーク。人間の成功率（約72%と報告）と比較されます。

        

        

          
テイクオーバーtakeover

          
エージェントの操作を人間が引き継ぐ・承認すること。重要な操作の前で一時停止して人に判断を仰ぐ使い方が一般的で、安全層の要です。

        

        

          
アクセシビリティツリーaccessibility tree

          
OSやブラウザが支援技術向けに提供する、画面要素の構造情報（役割・名前・位置）。スクリーンショットの画像と併用すると、要素の特定が安定しやすくなります。

        

        

          
サンドボックスsandbox

          
外部から切り離した隔離環境のこと。CUAでは専用VMなどでエージェントを動かし、誤操作や攻撃の影響が本番環境や個人のPCに及ばないようにします。
