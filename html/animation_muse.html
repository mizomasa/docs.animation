2. セキュリティのアーキテクチャ

公式ブログが示す要点は、MuseのVMは「root権限を持つLLMエージェントが自由に動く場所」ではない、ということです。1台のマシン上に隔離された2つのセキュリティ領域があります。信頼できないデータの処理が想定されるランタイムセルの外に、安全を担うサービスを置くのが骨格です。 公式情報

USER intent / consentユーザーの意図と同意
Muse clients / Main UIアプリから話しかける
Approvals承認ダイアログ（クライアントUIに直接表示）
Credential Capture UIパスワード等は専用UIからauthdへ直接。Museには見えない

🖥️ User's VM — Ingress（TLS + Noise）を経て中へ

🟩 Runtime cell（ランタイムセル）

systemd-nspawnコンテナ。信頼できないデータの処理が想定される領域。

  • Hatchデーモン（中核の実行基盤）＋ agentic harness
  • ワークスペースとファイル、メモリ、Persistent Storage（LUKS暗号化）
  • Museが実行するすべてのツール・バイナリ
  • guest root ≠ host root（セル内のrootはホスト側では無権限ユーザーにマッピング）
  • 独自のrootファイルシステム、仮想ネットワーク、フィルタ済みシステムコール（io_uringなし）、CAP_SYS_PTRACEなし／CAP_NET_ADMINなし
🛡️ hatch-safety（セル外）

モデル推論への入出力を検査する独立したモデル群と分類システム。プロンプトインジェクション等を検出。セル外なので攻撃者が無効化できない。

🔐 hatch-authd — Secure Credential Storage（セル外）

OAuthトークン等をMetaの一元インフラではなくユーザーのVM内に保管。メインエージェントは本物の認証情報を決して見ない。セル内にはサロゲート（代理）トークンだけが見え、実際の通信時にSentinelが本物へ差し替える。

🚦 Sentinel（セル外）— 唯一の許可権限

コネクターのアクションとネットワーク送信（イーグレス）の許可はSentinelだけができる。ポリシーを評価し、許可／拒否／ユーザーへの問い合わせを決める。L4/L7評価、SSRF検証、TLS検査、認証情報の挿入も担う。

⚙️ その他のホスト側サービス（別々のsystemdユニット）

privsep + broker：組み込みコネクターの実処理をセル外で限定権限で実行。ワーカーごとに認証情報の範囲を制限（例：カレンダー用ワーカーはメール認証情報を要求できない）。ブラウザのCDP接続もセル外のブローカーが管理。
postgres：永続的なアプリ設定を、セル・認証情報ストアとは別のDBに保存。
Inference proxy / telemetry proxy：外部インフラへの制限された経路。

セル ⇔ ホスト側サービスの通信はすべて Unixドメインソケット ＋ SO_PEERCRED ＋ ピアACL（カーネル認証の最小権限IPC）

承認の仕組み（公式どおり） 公式情報

Sentinelがユーザーに問い合わせると判断すると、実行は停止し、保留中の承認が作られます。承認ダイアログはMuseとの会話経由ではなく、クライアントUI内に直接表示され、ユーザーの回答もSentinelへ直接送られます。会話上の提案ではなく、厳格な機能としての承認です。

付与は特定のコネクターやリンク先、ユースケースに限定され、範囲つきで与えられます。Sentinelが選べる付与タイプを決め、以降の呼び出しが付与された範囲と正確に一致することを保証します。

1回限りセッションタスク期間（時間制限）無期限

人の介入なしに進むもの：読み取り専用のアクション、すでに許可されたアクション、低リスクと証明されたアクション。すべてを尋ねるわけではなく、同意が重要な場合にだけ手続き上の障壁を設ける設計です。

tainted egress（汚染追跡） 公式情報

ユーザーデータを読んだプロセスは「汚染（tainted）」されます。各ツールの実行プロセスはクリーンな状態で始まり、ユーザーデータを読み込むと汚染されます。

  • クリーンで、狭い自動許可ポリシーに適合し、URLチェックも通過したリクエストだけが、ユーザーを煩わすことなく自動許可される
  • 汚染された／検証できないリクエストは自動許可を失い、通常の承認フローへ戻る
  • 実装はeBPFによるネットワーク遮断・プロセス帰属・汚染伝播（LSMフック）

最小権限 公式情報

  • APIキーをモデルに決して見せない（見る必要がないものは見せない）
  • 読み取りと書き込みのアクセスを分離できる（基盤サービスが対応する場合）
  • OAuthの粗いスコープを超えて、コネクター／プロセス／認証情報／リクエスト単位で細かく制御できる
  • メールコネクターは、ワンタイムコード、パスワードリセットリンク、ログインマジックリンクを決定性フィルターと分類モデルで除外する

多層防御 —「致命的な3要素」を断つ 公式情報

Simon Willisonの「致命的な3要素」＝プライベートデータへのアクセス × 信頼できないコンテンツ × 外部通信の組み合わせを断つ設計です。

  • モデルレベルのトレーニングと、外部データへの「信頼できない入力」ラベル付け
  • 独立した検出分類システム群（hatch-safety）
  • VMからデータを移すアクションへの人間承認
  • ランタイムセル／privsep／authd／Sentinelによる決定論的な境界

ブラウザと購入 公式情報

  • CDP接続はセル外のブローカーが管理。ブラウザ用サブエージェントは生のDOMではなくアクセシビリティツリーのスナップショットだけを見る。ページ内JavaScript実行はできない
  • パスワードは専用UIからauthdへ直接送られ、エージェントには見えない
  • 購入はチェックアウト検知で毎回ユーザー承認が必須。ウォレット（Stripe Link等）では使い捨てカード番号が加盟店に渡り、認証情報は加盟店・金額・有効期間に紐づく

データポリシーと Confidential VM 公式情報

  • ファイルや記憶はすべてユーザーのVMに保存され、検証・編集・ダウンロード可能。会話やデータを広告システムと共有しない
  • 推論の軌跡は個人情報を除去したうえでモデル改善に使われることがあるが、設定でオプトアウト可能
  • Muse Confidential VM：Meta自身もVM内データにアクセスできないようにする機密VMを開発中（今年中に提供予定、外部監査つき）
  • 正直な留保：現行アーキテクチャでは、運用上必要な場合のMetaのアクセスは阻止されない

5. よくある誤解の解消

誤解：普通のチャットAIと何が違うの？

大きな違いは3つです。自分のコンピュータと作業場所があるので、作ったファイルやページが会話を閉じても残ります。覚えているので、決めごとや好みを次の会話でも使えます。そして頼まれれば定期的に勝手に動くので、毎朝のメール確認のような定期的な仕事を人なしで回せます。

誤解：メモリは無限に覚えていられる？

無限ではありません。「今の会話の文脈」は有限で、会話が長くなると古い部分は要約に圧縮されます。ずっと残るのは、ファイルに書き出された長期メモリ（決めごと・好み・人間関係など）です。だから大事な条件は「覚えておいて」と言ってファイルに残すのが確実です。

誤解：何でも勝手にやってしまうの？

いいえ。Museがアクションを提案しても、実行を許可できるのはセル外のSentinelだけです。問い合わせが必要な場合は、承認ダイアログが会話ではなくクライアントUIに直接表示され、回答もSentinelへ直接送られます。承認は1回限り／セッション／タスク／期間／無期限といった範囲つきで、購入は毎回承認が必須です。一方、読み取り専用や許可済み・低リスクのアクションは人の介入なしに進みます。

6. この図の根拠

この図は「盛って」描いたものではありません。説明の出どころを4種類に分けて明示します。各部品のカードにつけたラベルも、この分類に対応しています。

公式情報

Metaの公式ブログ 「Security and safety for AI agents: our approach with Muse」（muse.ai/blog） で公開されていることです。VM内部の分離構成は、このブログで公開されています。

  • VMは2つのセキュリティ領域：ランタイムセル（systemd-nspawn）と、セル外のホスト側安全サービス
  • hatch-safety／hatch-authd（サロゲート）／Sentinel（唯一の許可権限）／privsep／Postgres／推論・テレメトリプロキシ、Unixソケット＋SO_PEERCRED＋ピアACL
  • 承認はクライアントUIに直接表示され、範囲つき付与（1回限り／セッション／タスク／期間／無期限）が可能。読み取り専用・許可済み・低リスクは人の介入なし
  • tainted egress、最小権限、メールコネクターの保護、多層防御と「致命的な3要素」、ブラウザブローカー、購入時の毎回承認
  • データポリシー（ファイル・記憶はユーザーのVMに保存、広告システムと共有しない、軌跡のオプトアウト可能）と、開発中のMuse Confidential VM
  • ユーザーごとに専用のエージェントとコンピュータ、コネクタの存在、モデルはMetaのMuseモデルファミリーであること

利用実態で確認できること

このユーザーが実際に使っていて、目に見えていることです。

  • 毎朝のメール確認のような定期的な作業が、スケジュールで自動実行されている
  • メモリに希望を言うと保存され、次の会話で使われる
  • 作ったページやファイルが残り、後から開ける
  • サブエージェントに分けた仕事の結果が返ってくる
  • 購入や送信の前に承認カードで確認される

概念的な説明

仕組みを分かりやすくするためのモデル化・言い換えであり、Metaの内部実装そのものではありません。

  • 「専用のコンピュータ」「手順書」といった言い換え
  • 部品の分け方や、矢印で示した情報の流れ
  • メモリを「2層」と整理して描く見取り図
