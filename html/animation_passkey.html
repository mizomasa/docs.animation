パスキーは、どうやってログインさせるのか

パスキー（WebAuthn / FIDO2）の動きを、登場人物のあいだで何が飛び交っているかで追うアニメーションです。再生ボタンかステップ送りで、登録と認証の流れを1手ずつ確認できます。各ステップには利用者のスマホ画面の移り変わりも連動して表示されます。

色分けが要点です。秘密鍵や生体情報がサイト側のサーバーへ送られることはありません。ただし、ログイン時に送られるのは署名だけではなく、クレデンシャルID・clientDataJSON・authenticatorDataなどを含む認証レスポンスです。

    パスワード方式と何が違うのか

    パスワードは利用者が入力した秘密をサーバーへ送り、サーバー側の検証用情報と照合します（通常はHTTPSで保護され、サーバーにはソルト付きハッシュなどを保存します）。パスキーは秘密鍵をサイト側サーバーに渡さず、公開鍵で署名を検証します。

    パスワード方式

    • ログインのたびに入力したパスワードをサーバーへ送る（通常はTLSで暗号化）
    • サーバー側にも照合用の情報が保管され、漏洩すると悪用される
    • 偽サイトに本物のパスワードを入力してしまう（フィッシング）
    • 他のサイトと使い回すと、1件の漏洩が連鎖する

    パスキー

    • サーバーへ送られるのは署名を含む認証レスポンス。秘密鍵そのものは送られない
    • サーバーが保管するのは公開鍵やクレデンシャルIDなど。公開鍵だけでは署名を作れない
    • OriginとRP IDが認証データ・署名に結びつくため、偽サイトでは本物のサイト用パスキーを使えない
    • 鍵はサイト・アカウントごとに別々に作られるので、使い回し自体が起きない

    用語ミニ解説

    アニメーションに出てくる言葉の早見表です。勉強会の質疑の補助にどうぞ。

    CHALLENGEチャレンジ

    サーバーが毎回発行する使い捨てのランダムな値。「さっきの使い回し」ではなく「今この場で作った署名」であることを保証し、盗聴した署名の再利用（リプレイ攻撃）を防ぎます。

    SIGNATURE署名

    秘密鍵でしか作れない、データに付けられる「印」。公開鍵で「本物かどうか」だけ検証できますが、署名から秘密鍵を逆算することはできません。

    AUTHENTICATOR認証器

    鍵ペアを生成・保管し、署名を行う装置。スマホやPC内蔵のもの（Touch ID、Windows Hello、Androidの指紋認証など）と、USBセキュリティキーがあります。

    CREDENTIAL IDクレデンシャルID

    認証器が生成する「どの公開鍵クレデンシャルか」を示す識別子です。サーバーはこれを手がかりに登録済みの公開鍵を探します。IDだけでは署名を作れないため、漏れてもログインはできません。

    USER HANDLEユーザーハンドル

    サーバー（RP）がアカウントごとに指定する不透明な識別値です。発見可能なクレデンシャルでは認証器に保存され、ユーザー名を入力しない認証で返されます。仕様上、メールアドレスやユーザー名などの個人情報を含めてはいけません。

    RP ID / ORIGINドメインの結びつけ

    RP IDはパスキーを結びつけるドメイン名（スキームやポートは含まない）です。Originはスキーム・ホスト・ポートの組です。OriginはclientDataJSONに、RP IDのSHA-256ハッシュはauthenticatorDataに入り、両方が署名で保護されます。

    WEBAUTHN / FIDO2WebAuthn と FIDO2

    ブラウザのJavaScript APIが WebAuthn、認証器との通信規格が CTAP、合わせて FIDO2 と呼ばれます。パスキーはこの標準の上で動く仕組みの総称です。

    SYNCED PASSKEY同期パスキー

    iCloudキーチェーンやGoogleパスワードマネージャーで、自分の端末間に同期される方式。この場合、秘密鍵は同期サービスを通じて暗号化された形で端末間に共有されます（サーバー＝RPへ送られることはありません）。USBキーなどのデバイスバウンド型では、秘密鍵はその認証器の外へ出ません。同期アカウント自体の守りが重要になります。

    このアニメーションは WebAuthn（FIDO2）の概念モデルを勉強会向けに簡略化したものです。実際の認証レスポンスにはcredential ID、clientDataJSON、authenticatorData、signatureが含まれ、発見可能なクレデンシャルを使うユーザー名なしの認証ではuserHandleも返されます。署名はauthenticatorDataとclientDataJSONのハッシュを対象に作られます。OriginとRP IDは別の値です。また、User Verification（UV）は常に必須ではなく、RP側の設定によりUser Presence（UP）のみを求める場合もあります。
