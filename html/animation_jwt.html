JWTの仕組みアニメーション

JWT（JSON Web Token）は、ログイン後にサーバーが発行する「署名付きの身分証」のような文字列です。ブラウザがリクエストのたびに添えて送り、サーバーは署名を確かめるだけで「本物かどうか」が分かります。8ステップで発行から検証、改ざんが弾かれる様子まで追ってみましょう。

JWTの分解図 — 3つの部分

JWTはドットで区切られた3つの文字列です。各部分はJSONなどを Base64URL で符号化したもの。

① ヘッダー（赤）

署名の方式などを書く部分。

{
  "alg": "HS256",
  "typ": "JWT"
}

② ペイロード（青）

ユーザー情報や有効期限（クレーム）を書く部分。

{
  "iss": "auth.example.jp",
  "sub": "user_42",
  "role": "user",
  "iat": 1763364800,
  "exp": 1763368400
}

③ 署名（緑）

署名 = HMACSHA256( Base64URL(ヘッダー) + "." + Base64URL(ペイロード), 鍵 )。ヘッダーとペイロードを鍵で計算した結果で、1文字でも書き換えると一致しなくなります。

⚠ 大事な誤解ポイント：ペイロードは暗号化されていません。Base64URLは「符号化（エンコード）」にすぎず、誰でもデコードして中身を読めます。署名の役割は「隠すこと」ではなく「改ざんを検知すること」。だからパスワードや個人情報など、見られて困る情報をペイロードに入れてはいけません。

署名方式の比較：HS256 と RS256

HS256（HMAC）RS256（RSA署名）
鍵共通鍵（1つの秘密の文字列）秘密鍵と公開鍵のペア
署名する側共通鍵を持つ認証サーバー秘密鍵を持つ認証サーバーだけ
検証する側同じ共通鍵が必要公開鍵で検証できる
向いている場面発行も検証も同じシステム内検証するサーバーが複数ある／外部サービスと連携
注意点共通鍵が漏れると誰でも偽造できる。検証側にも鍵を配る必要がある公開鍵は配っても安全。鍵管理の仕組みはやや複雑
補足 3

セッション方式との違い

セッション方式

  • サーバー側にログイン状態（セッション）を保存する
  • ブラウザにはランダムなセッションIDだけを渡す
  • ログアウトや強制失効がすぐできる
  • サーバーが増えるとセッションの共有が必要になる

JWT方式

  • サーバー側に状態を持たない（ステートレス）
  • 検証は署名チェックだけで完結し、DB照会が不要
  • サーバーを増やしてもそのままスケールしやすい
  • 有効期限が切れるまで失効させにくい（盗まれたら期限まで有効）→ 対策として有効期限を短くし、リフレッシュトークンと組み合わせるのが定番
補足 4

JWTの保管場所と注意点

保管場所特徴と注意
localStorage実装は簡単だが、JavaScriptから読み取れるため XSS（クロスサイトスクリプティング）攻撃で盗まれやすい。機密性の高い用途では避けるのが無難。
HttpOnly CookieJavaScriptから読めないためXSSで盗まれにくい。一方でリクエストに自動送信されるため、CSRF対策（SameSite属性やCSRFトークン）とセットで使う。
メモリ内（変数）最も盗まれにくいが、ページを再読み込みすると消える。リフレッシュトークンで再取得する設計と組み合わせることが多い。
  • 有効期限（exp）は短めに設定し、自動更新の仕組みを用意する
  • HTTPSで送ることを前提にする（平文HTTPでは盗聴される）
  • サーバー側は alg を鵜呑みにせず、想定した署名方式だけを許可する（alg: none 攻撃対策）
補足 5

用語解説

クレーム（Claim）

ペイロードに書かれる情報の項目。iss（発行者）、sub（対象ユーザー）、exp（有効期限）、iat（発行時刻）など。カスタム項目（roleなど）も追加できる。

Base64URL

データをURLに載せても安全な文字だけで表す符号化方式。通常のBase64の「+」「/」を「-」「_」に置き換え、末尾の「=」を省く。暗号化ではない。

Bearerトークン

「持っている人（Bearer）が本人」とみなすタイプのトークン。だからこそ盗まれると悪用される。HTTPでは Authorization: Bearer <JWT> の形で送る。

署名（Signature）

ヘッダーとペイロードを鍵で計算した値。中身が1文字でも変われば署名は一致しなくなり、改ざんを検知できる。
