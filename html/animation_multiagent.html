マルチエージェントの仕組みアニメーション

大きなタスクを1つのエージェントで抱え込まず、司令塔（オーケストレーター）が仕事を分割し、複数のサブエージェントに並行して調べさせて、最後に結果を1つにまとめる。 その「分担 → 並行実行 → 統合」の流れを、9ステップで再生できます。

NOTES

なぜ分けるのか

1つのエージェントに全部やらせるのと比べて、サブエージェントに分けると何が得られるのか。理由は大きく3つあります。

コンテキストが汚れない

宿の候補を何十件も読み込む作業を司令塔自身がやると、その細かい情報で司令塔の文脈（コンテキスト）が埋まってしまいます。サブエージェントが自分の文脈の中で読み込み、司令塔には要約だけが返るので、司令塔は全体の見通しを保ったまま判断できます。

並行化で速い

宿 → 交通 → 見どころを順番に調べると、所要時間は3つの合計になります。同時に走らせれば、いちばん遅い1つの時間で済みます。互いに依存しないサブタスクほど、この効果が大きくなります。

専門特化させられる

サブエージェントごとに指示・使えるツール・（製品によっては）モデルを変えられます。「宿担当は予約サイト検索だけ」「交通担当は時刻表ツールだけ」のように役割を絞ると、迷いが減って精度が上がります。

NOTES

コストと限界

分ければ万能、ではありません。マルチエージェント化にははっきりした代償があります。

トークン消費が増える

サブエージェントの数だけ、指示の読み込みと推論が走ります。3人に分ければ、ざっくり3人分のコストです。並行化で時間は買えますが、料金は増えるのが基本です。

統合という仕事が生まれる

結果はバラバラの粒度・形式で返ってきます。矛盾の調整、重複の除去、最終回答への組み立ては司令塔の仕事で、ここが雑だと「分けたのにまとまらない」結果になります。サブタスク同士の依存が強い課題ほど統合は難しくなります。

単純なタスクには過剰

1回のツール呼び出しで済むような依頼にまで分解すると、起動と待ち合わせの手間だけが増えて遅くなります。「分割できるか」ではなく「分割する価値があるか」が判断基準です。目安は、調査範囲が広く、独立に進められて、結果が要約で済むタスクかどうかです。

NOTES

連携パターンの違い

今回のアニメーションは「司令塔型」です。エージェント同士のつなぎ方には、他にも代表的な型があります。

司令塔型（オーケストレーター）

あなた → 司令塔
司令塔 → A・B・C（並行）
A・B・C → 司令塔 → あなた

中心の司令塔が分解・配布・統合を担い、ワーカーは互いを知りません。全体像は司令塔だけが持ちます。今回の構成で、並行調査や大量処理に向きます。

引き継ぎ型（ハンドオフ）

あなた → 受付エージェント
　→ 専門エージェント
　→ 別の専門エージェント

会話の主導権そのものを次のエージェントへ渡します。「一次受付が内容を聞き、専門担当にバトンタッチする」ような流れで、引き継いだ側があなたと直接やり取りを続けます。

順番型（パイプライン）

入力 → 工程1 → 工程2 → 工程3 → 出力
（下書き → 校正 → 整形 など）

前の工程の出力を次の工程の入力にする一本道です。並行にはなりませんが、工程ごとに指示と品質基準を固定でき、再現性が上がります。

NOTES

サブエージェントへの指示の書き方

サブエージェントは生まれたての状態で起動し、あなたと司令塔の会話履歴は共有されません。だから指示は「それだけ読めば仕事が完結する」自己完結な形で渡すのが鉄則です。

良い指示の例（Aへの指示）

# タスク 旅行先エリアの宿を調べ、候補を3件に絞ること。 # 期待する成果物 候補ごとに「名前／1泊の目安価格／特徴を1行」を箇条書きで。最後に推薦を1件。 # 制約 予算は1泊2万円まで。公式サイトか予約サイトで確認できた情報だけを使うこと。 分からない項目は「未確認」と書くこと。
  • タスク：何をしてほしいか。背景も含め、その場で判断できる材料を渡す
  • 期待する成果物：形式と量を決める。統合する側（司令塔）が受け取りやすい形に
  • 制約：予算・情報源・禁止事項。書かれていない前提は伝わらないと思って書く
  • 逆に「さっき話した条件で」のような指示は通用しません。会話履歴が見えない相手への引き継ぎメモだと考えるのが近道です
NOTES

用語解説

オーケストレーションorchestration
複数のエージェントや処理の段取りを、中心役が指揮して全体を進めること。分解・配布・待ち合わせ・統合までを含む、司令塔の仕事全体を指します。
ハンドオフhandoff
処理の主導権を別のエージェントへ引き継ぐこと。司令塔型と違い、引き継いだ側がそのまま対話や処理を続行します。
コンテキスト分離context isolation
エージェントごとに会話・作業の文脈を独立させること。細部の情報が他へ漏れ広がらず、各エージェントは自分の仕事に集中できます。代わりに、必要な情報は指示として明示的に渡す必要があります。
並行実行parallel execution
複数のサブエージェントを同時に走らせること。全体の所要時間は「合計」ではなく「最も遅い1つ」に近づきます。互いに依存しないサブタスクでのみ可能です。
サブタスクsubtask
大きなタスクを分解した個々の仕事。「宿を調べる」「交通を調べる」のように、それ単体で完了を判定できる粒度に切るのがコツです。
ワーカーworker
司令塔からサブタスクを受けて実際に手を動かす側のエージェント。サブエージェントとほぼ同じ意味で、司令塔型の構成でよく使われる呼び方です。
このページのタスク例（旅行先の宿・交通・見どころの調査）や進捗の数値は、仕組みを説明するための一般的な例です。実際の製品では、サブエージェントの起動方法・並行数の上限・結果の受け渡し形式はフレームワークごとに異なります。
