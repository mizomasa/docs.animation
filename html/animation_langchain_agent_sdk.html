LangChainとAgent SDK：フレームワークの動き

LangChainとAgent SDK（Claude Agent SDK／OpenAI Agents SDK）は、どちらもLLMアプリを作るための枠組みです。 違いは「どこまで枠組みが面倒を見るか」。 このページでは、開発者が書く部分とフレームワークが担う部分を色で分けながら、 部品の流れとループの動きをアニメーションで追います。

開発者が書く・決める部分 フレームワークが担う部分 流れるデータ（玉） この色分けはページ全体で共通です
SECTION 1

全体像：2つの設計思想

LangChainは「部品を組み立てる」発想、Agent SDKは「ループを内蔵する」発想。まず全体の形を並べて見ます。

LANGCHAIN

モデル・プロンプト・ツール・メモリといった部品はフレームワークが用意します。 ただし、どの部品を・どの順序でつなぐか（流れそのもの）は開発者が設計します。 部品同士は鎖（チェーン）のようにつながり、データはその鎖を順に流れます。 流れがコードにそのまま見えるので、途中で何が起きるかを細かく制御できます。

AGENT SDK

↓ 渡す
AGENT SDK（フレームワーク）
考える → 道具を使う → 結果を見る → また考える…
この繰り返し（エージェントループ）そのものがSDKの中に入っている

エージェントループそのものがSDKに組み込まれています。 開発者が書くのはタスク・ツール・制約の3つだけで、 「モデルに聞く → ツールを実行する → 結果を戻す」という往復の制御は書きません。 手順が事前に決まらない仕事を、モデル自身の判断で進められます。

LCEL（LangChain Expression Language）— パイプ記法で鎖を書く
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_template(
    "会話履歴:\n{history}\n\n質問: {question}")
model = ChatOpenAI()          # 使うモデルを選ぶ
parser = StrOutputParser()    # 出力を文字列に整える

# パイプ（|）で部品をつなぐ ＝ 上の図の鎖そのもの
chain = prompt | model | parser
answer = chain.invoke({
    "history": "（メモリ部品が読み出した過去の会話）",
    "question": "明日の東京の天気は？傘は要る？"})

※ メモリは「読み出した履歴をプロンプトの {history} に渡し、終わりに今回のやり取りを保存する」配線として鎖に組み込みます（ステップ2・8）。ツールを使う構成では、モデルにツールを結びつけ、ツール実行の部品を鎖の途中に加えます（ステップ5〜6）。分岐やループが必要になったら、次のLangGraphの出番です。

SECTION 3

LangGraph：分岐とループは「グラフ」で組む

鎖は直線が基本なので、「足りなければ調べ直す」のような分岐・ループは苦手です。 LangChain系でそれを扱うのが LangGraph。 処理をノード、遷移をエッジとし、共有されるデータの入れ物＝状態（State）がグラフを巡ります。 題材は「文書を検索して答える」処理です。

Claude Agent SDK（Python）の例

              
from claude_agent_sdk import query, ClaudeAgentOptions

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Glob"])

async for message in query(
    prompt="資料フォルダから関連ファイルを
            探して要約して",
    options=options):
    print(message)

            

            

              
OpenAI Agents SDK（Python）の例

              
from agents import Agent, Runner

agent = Agent(
    name="researcher",
    instructions="資料を調べて要約する",
    tools=[search_files, read_file])

result = await Runner.run(
    agent, "資料を探して要約して")

        SECTION 5
        
比較表：どちらを選ぶか

        
優劣ではなく、抽象度（どこまで任せるか）の違いです。同じ仕事を両方で組むこともできます。

      


      

        

          
            

              観点
              LangChain / LangGraph部品組み立て型
              Agent SDKループ内蔵型
            

          
          
            

              抽象度
              低め — 部品と流れが見える分、細かく制御できる。代わりに設計と配線は自分で担う
              高め — ループごと任せる分、早く動く。代わりに内部の細部はSDKの流儀に従う
            

            

              開発者が主に書くもの
              部品の組み合わせ、流れ（鎖／グラフ）の設計、状態の持ち方
              タスク（指示）、ツール定義、許可や制約。ループ制御は書かない
            

            

              分岐・ループの扱い
              チェーンは直線が基本。分岐・ループはLangGraphで、ノードとエッジとして自分で設計する
              エージェントループが内蔵。回数や順序はモデルの判断に委ねられる
            

            

              向いている用途
              手順の決まった処理、RAGのようなパイプライン、途中の形式や順序を厳密に決めたい処理
              調べもの、ファイル操作、試行錯誤が要る作業など、手順が事前に決まらない自律的なタスク
            

            

              関係
              
                対立するものではありません。Agent SDK的な自律エージェントも、LangChain側ではLangGraphで組めます。
                逆にAgent SDKでも、ツールの裏側に決まった手順の処理（チェーン的な処理）を置けます。
                選ぶ基準は「流れを自分で設計したいか、モデルの判断に任せたいか」です。
              
            

          
        

      


      
      

        SECTION 6
        
用語解説

        
このページで使った言葉の整理です。

      


      

        

          
チェーンChain

          
部品を鎖のようにつないだ処理の流れ。入力が先頭の部品から順に渡され、最後の部品の出力が結果になる。LangChainの基本単位で、各部品は「入力を受けて出力を返す」という共通の約束（Runnableインターフェース）でつながる。

        

        

          
LCELLangChain Expression Language

          
チェーンをパイプ記法で書くための記法。prompt | model | parser のように、部品を | でつなぐだけで鎖になり、invoke で実行できる。ストリーミングや並列実行などの共通機能も、この記法で組んだ鎖に自動で付いてくる。

        

        

          
ノードとエッジと状態LangGraph

          
ノード＝1つの処理（関数）。エッジ＝ノード間の遷移で、状態の中身に応じて行き先が変わる「条件付きエッジ」もある。状態（State）＝グラフ全体で共有されるデータの入れ物で、各ノードが読み書きしながら処理が進む。分岐・ループ・途中での停止と再開はこの仕組みで表す。

        

        

          
エージェントループAgent Loop

          
「モデルが考える → ツールを使う → 結果を見る → また考える」の繰り返し。モデルが「もう道具は要らない」と判断するまで続くため、回数は実行時に決まる。Agent SDKではこのループがSDK側に内蔵され、LangGraphでは開発者がグラフとして設計する。

        

        

          
抽象度Abstraction

          
「細部をどれだけ枠組みの内側に隠すか」の度合い。低い＝部品と流れが見えて細かく制御できるが、書く量と設計の責任が増える。高い＝渡すものが少なく早く動くが、内部の挙動は枠組みの流儀に従う。どちらが良いかは、作るものの性質で決まる。

        

        

          
ツール呼び出しTool Calling

          
モデルが「このツールを、この引数で呼んでほしい」という指示（tool_use）を返す仕組み。モデル自身は外部に触れられないので、実際に実行するのはフレームワーク側。実行結果（tool_result）がモデルに戻され、次の生成に使われる。

        

      


      

        どちらの道でも、モデルとツールは同じ。
        違いは「流れの設計図を誰が持つか」だけです。決まった手順を確実に回したいなら設計図を自分で描く（LangChain／LangGraph）、
        手順自体をモデルに考えさせたいなら設計図ごと任せる（Agent SDK）。
        実際の開発では、全体はSDKに任せつつ、部分的に決まった処理をツールの中に閉じ込める、といった混ぜ方もよくあります。
      


      

        コード例は各フレームワークの公開APIに基づく最小限の抜粋です。正確な仕様は各公式ドキュメント（LangChain／LangGraph、Claude Agent SDK、OpenAI Agents SDK）を確認してください。
