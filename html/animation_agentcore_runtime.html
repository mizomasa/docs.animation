AgentCore Runtimeの仕組み

Amazon Bedrock AgentCore Runtimeは、AIエージェントのコードを本番環境で動かすための、AWSのマネージドな実行基盤です。 鍵になるのは「セッション」という単位で、会話ごとに専用の microVM が割り当てられ、状態を保ったまま最長で8時間動き続けます。 まずセッションのライフサイクルを8ステップで再生し、そのあと背景・仕組み・注意点を文章で見ていきます。

概要

AgentCore Runtimeは、AIエージェントを本番環境で動かすための、AWSのマネージドな実行基盤です。

エージェントの実行には「利用者ごとに状態を持つ」「処理が分単位から時間単位まで長くかかる」「他人のデータと混ざってはいけない」という性質があり、通常のWebサーバーや関数実行の基盤では受け止めきれないために生まれました。

会話（セッション）ごとに専用のmicroVMが割り当てられ、状態を保ったまま最大8時間動き続けられるので、開発者はインフラではなくエージェント本体に集中できます。

背景

AgentCore Runtimeが生まれた背景 — 「作る」から「動かし続ける」へ

フレームワークが解いたのは「作る」まで

Strands AgentsやLangGraphのようなフレームワークの登場で、エージェントを「作る」こと自体はぐっと簡単になりました。モデルにツールを持たせてループを回せば、手元のPCではそれらしく動きます。ところが本番に出そうとすると、作る段階にはなかった問題が並び始めます。エージェントの実行を「どこで、どういう境界で、どれだけ長く」動かすかという、運用側の問題です。

セッションが混ざる危険

エージェントは利用者ごとに状態を持ちます。会話の履歴、途中の計算結果、ツールに渡す認証情報まで、セッションの中に抱え込むのです。実行環境を大勢で共有する作りだと、ある利用者の状態や認証情報が、別の利用者の処理に漏れる事故が起きかねません。エージェントは利用者の代わりにデータベースや外部サービスへ触る「特権的な処理」をするため、この境界の曖昧さはそのままセキュリティの問題になります。

エージェントの処理は長い

通常のAPIリクエストは秒単位で終わりますが、エージェントの処理はモデル呼び出しとツール実行を何度も繰り返し、長い調査や複数ステップの作業では時間単位に及ぶこともあります。一般的なサーバーレス関数には実行時間の上限があり（たとえばLambdaは15分）、その枠にエージェントの仕事は収まりません。かといって常駐サーバーにすると、今度は会話と会話のあいだの長い待機時間にも資源を割り続けることになります。

スケールとアイドルコストの板挟み

利用者が増えれば同時セッションは大きく膨らみ、減ればゼロに近づきます。ピークに合わせてサーバーを用意すればアイドル時間の無駄が大きく、リクエストごとに環境を作り直せば状態が消えて会話が続きません。「利用者ごとの分離」と「状態の保持」と「使った分だけの課金」を同時に満たす実行基盤が要る、というのがRuntimeの出発点です。

ないとどうなるか

こうした基盤がなければ、エージェントを本番に出すチームは、コンテナ基盤の上にセッション管理、利用者ごとの分離、長時間実行、スケーリングの仕組みを自前で作り込むことになります。作れないものではありませんが、その工数はエージェント本体の改善には向かいません。Runtimeは、この「エージェントの下回り」をAWS側が引き受けるという製品です。

        SECTION 2
        
画面でこう見える — デプロイと呼び出し

        
開発者の作業は大きく3つです。エージェントのコードを用意し、Runtimeへデプロイし、あとは呼び出し側から「ARN＋セッションID」で叩く。セッションやmicroVMの管理コードは書きません。

      

      

        
ターミナル — デプロイから呼び出しまで

        
# 1. エージェントのコードを用意する（入口を決めるだけ）
from bedrock_agentcore.runtime import BedrockAgentCoreApp

app = BedrockAgentCoreApp()

@app.entrypoint
def invoke(payload):
    # ここにエージェントの処理。フレームワークは自由
    ...

# 2. Runtimeへデプロイする（スターターツールキット）
$ agentcore configure -e agent.py
$ agentcore launch
→ デプロイ完了。エージェントのARNが払い出される

# 3. 呼び出し側は、ARNとセッションIDを指定して叩く
InvokeAgentRuntime(
    agentRuntimeArn = "arn:aws:bedrock-agentcore:...:runtime/…",
    runtimeSessionId = "user42-conv-9f3…",
    payload = { "prompt": "先月の出張経費が規定に合っているか調べて" },
)

      

      
コードとコマンドは説明用のイメージです。実際の手順やSDKの形は公式ドキュメント（スターターツールキット／AgentCore CLI）を確認してください。

      

        

          
コンテナでも、コードのままでも deploy

          
公式FAQでは、デプロイ方法としてコンテナイメージ（最大10GB）を使う方法と、コードをZIPで直接アップロードする簡易な方法の2つが案内されています。Runtimeが求めるのは「決められた形のHTTPの口をコンテナの中で用意すること」で、中の実装言語やフレームワークは問いません。

        

        

          
呼び出し口は「ARN＋セッションID」 invoke

          
デプロイされたエージェントはARNで特定され、呼び出しは InvokeAgentRuntime にセッションIDを添えて行います。同じIDなら同じセッション、違うIDなら新しいセッション。この単純な規則が、会話の継続と利用者ごとの分離を両立させる中心の仕掛けです。

        

      


      
      

        
読み物

        
仕組みを文章で読む — セッションという単位

        
アニメーションを再生しなくても流れが追えるよう、同じ内容を文章でもたどっておきます。

        
セッションとmicroVM

        
Runtimeの中心の単位はセッションです。呼び出し側は会話ごとに runtimeSessionId を決めて渡し、同じIDへの呼び出しは同じ実行環境へ届きます。各セッションには専用のFirecracker microVM（Lambdaなどでも使われている軽量な仮想マシン）が割り当てられ、CPU・メモリ・ファイルシステムがセッション単位で分離されます。セッションが終わればmicroVMごと破棄され、メモリは消去されるため、前の利用者のデータが次の利用者に残ることはありません。

        
状態はセッションの中にだけ残る

        
セッションが生きている間、メモリやファイルに書いた内容はそのまま残り、次のターンで続きに使えます。逆に言えば、それはセッション限りの揮発性の状態です。セッションを越えて残したい会話履歴や利用者の好みは、セッションの外に置く設計が前提で、AgentCoreではその役割を兄弟サービスのMemoryが担います。

        
ライフサイクルと時間の上限

        
セッションには Active（処理中）、Idle（待機中）、Stopped（終了）の3つの状態があります。終了のきっかけは、アイドル時間の超過（既定15分）、最大ライフタイムへの到達、明示的な停止APIの呼び出しなどです。最大ライフタイムはmicroVMの場合で既定8時間となっており、設定により変更できます。公式FAQでは、インスタンス型のコンピューティングでは最大14日のセッションも案内されています。「最大8時間」という数字は、1つの会話・作業がどれだけ長く続いてよいかという、設計上の天井になります。

        
フレームワークとモデルは選ばない

        
Runtimeが求めるのは、決められた形のHTTPの口（呼び出しを受けるエンドポイント）を用意することであり、中で動くエージェントの作り方は問いません。公式FAQでは、Strands Agents、LangGraph、CrewAI、LlamaIndex、Google ADK、OpenAI Agents SDKなどが実例として挙げられています。使うモデルもAmazon Bedrockのものに限らず、外部のモデルでもかまいません。つまりRuntimeは「エージェントの頭脳」ではなく、「エージェントの置き場所」です。

        
対応プロトコル

        
呼び出しの基本形はHTTPですが、公式にはMCPとA2Aへの対応も案内されています。エージェント自体をMCPサーバーとして公開したり、A2Aで他のエージェントから呼ばれる形にしたりと、エージェント同士やツールとの共通規約に沿った公開ができます。公式ドキュメントでは、セッションを同じ環境へ届け続けるためのヘッダーが、プロトコルごとに定義されています。

        
AgentCoreファミリーの中のRuntime

        
AgentCoreは単一の製品ではなく、エージェント運用のためのサービスの集まりです。ツール接続を担うGateway、記憶を担うMemory、認証情報やトークンの管理を担うIdentity、隔離されたコード実行のCode Interpreter、ブラウザ操作のBrowser、観測のObservabilityなどが兄弟として並びます。その中でRuntimeは、エージェントのコードそのものを動かす土台であり、他のサービスは必要に応じて組み合わせる位置づけです。

      

      

        歩み。
        AgentCoreは2025年7月にプレビューが公開され、2025年10月13日に一般提供（GA）となりました。GAの時点で東京を含む9つのリージョンで提供され、VPCやAWS PrivateLink、AWS CloudFormationへの対応も含まれていたと、AWS公式発表で案内されています。
      


      
      

        
強みと弱み

        
AgentCore Runtimeの良い点と弱点

        
良い点：分離とスケールを「買える」

        
最大の利点は、セッションごとの分離とスケーリングを自作せずに済むことです。同時セッションがゼロから大きく増えても自動でさばかれ（公式FAQでは、数十万規模の同時セッションまで自動でスケールすると説明されています）、課金は実際に使ったCPUとメモリに対する秒単位の従量制で、モデルの応答待ちのようなI/O待ちの間はCPUがゼロにスケールします。エージェントの「待っている時間が長い」という性質と、課金の形が噛み合っているのです。

        
弱点：状態は揮発し、永続化は外付けが前提

        
セッション内の状態は、セッションと運命を共にします。重要なデータをセッションの中だけに置く設計はできず、永続化はMemoryや外部ストレージへ逃がす作りが必須になります。セッションIDと利用者の対応づけや、利用者ごとのセッション数の管理も、公式ドキュメントが注意書きしている通り、呼び出し側の責任として残ります。

        
弱点：中身はブラックボックスで、AWSに寄る

        
実行基盤を任せる代わりに、基盤の細部はAWS側の管理下に置かれます。特殊な実行環境の要件がある場合や、他のクラウドでもまったく同じ構成を再現したい場合には、自前のコンテナ基盤の方が自由は効きます。利便性と引き換えの依存であることは、導入前に織り込んでおきたい点です。

      


      
      

        SECTION 3
        
リスクと注意点 — 任せる範囲と残る責任

        
基盤を任せても、権限とコストとセッション管理の責任は消えません。公式ドキュメントで裏の取れる範囲で、代表的な注意点を並べます。

      

      

        

          
権限設計（IAM）

          
エージェントは、Runtimeに設定された実行ロールの権限で、AWSのリソースやツールに触ります。広すぎる権限は、そのままエージェントの誤動作や情報漏えいが届く範囲になります。

          
対策：最小権限が原則です。公式ドキュメントでは、セッションのコンテキストキーを使って、セッションごとにアクセスできる範囲（S3のプレフィックスなど）を絞る方法も案内されています。

        

        

          
コストの読み方

          
課金は、セッションが生きている間のCPUとメモリの実消費に対する秒単位の従量制です。I/O待ちではCPUの課金が下がる一方、メモリはセッション保持中ずっと対象になるため、止め忘れたアイドルセッションは静かにコストを積みます。

          
対策：アイドルタイムアウトを実態に合わせて設定し、不要なセッションは明示的に止めます。なお、モデルの推論料金はRuntimeとは別に発生します。

        

        

          
上限とコールドスタート

          
1セッションの上限はmicroVMで最大8時間です。それを超える作業は、途中経過をセッションの外に保存して引き継ぐ設計が要ります。また新しいセッションはmicroVMの起動を伴うため、初回の応答には起動分の時間がかかることがあります（公式ドキュメントでも、セッションが切り替わるとコールドスタートによる遅延がありうると説明されています）。

          
対策：長時間の処理は、応答を返したあとも裏で続ける「バックグラウンド実行」として切り出す設計が、公式ドキュメントで案内されています。

        

        

          
セッションIDの管理責任

          
どの利用者がどのセッションIDかという対応づけは、呼び出し側のアプリが保持するのが公式ドキュメントの前提です。IDの付け方や渡し方を誤れば、文脈が混ざったり、他人のセッションに届いたりしかねません。

          
対策：利用者ごとに一意で十分に長いID（公式ドキュメントでは33文字以上）を発行し、対応づけはバックエンドで管理します。プラットフォームの新しいバージョンでは、セッションを作成した利用者以外からのアクセスを拒否する仕組みも案内されていますが、自前の管理が不要になるわけではありません。

        

      

      

        「分離」は境界であって、認証そのものではありません。
        microVMの分離は「セッション同士が混ざらない」ことを守りますが、「Runtimeを呼んでよいのは誰か」は別の設計です。公式FAQでも、Amazon CognitoやMicrosoft Entra ID、Oktaといった既存のIDプロバイダと連携して、エージェントへのアクセスを制御する使い方が案内されています。
      


      
      

        
まとめ

        
まとめ

        
AgentCore Runtimeは、エージェントを「作る」ための道具ではなく、「本番で動かし続ける」ための置き場所です。会話ごとに専用のmicroVMを割り当て、状態を保ったまま最長8時間動き続け、終われば環境ごと消去する。この割り切りによって、利用者同士の分離、長時間実行、スケーリングという本番運用の難所をAWS側に寄せています。代わりに、状態の永続化や、セッションと利用者の対応づけは、開発者側の設計として残ります。フレームワークやモデルを選ばない作りなので、「頭脳は自由に作り、置き場所は借りる」という分担が、Runtimeの本質だと言えます。

      


      
      

        GLOSSARY
        
用語解説

      

      

        

          
セッションsession

          
1つの会話・作業に対応する実行の単位。セッションが生きている間、専用のmicroVMが状態を保持し続けます。Runtimeの管理と課金は、このセッションを単位に考えます。

        

        

          
runtimeSessionId

          
セッションを識別するID。呼び出し側が決めて渡し（公式ドキュメントでは33文字以上）、同じIDへの呼び出しは同じmicroVMへ届きます。利用者とIDの対応づけはアプリ側の責任です。

        

        

          
microVMFirecracker

          
軽量な仮想マシン。AWSのFirecracker技術で作られ、Lambdaなどでも使われています。Runtimeではセッションごとに1つ割り当てられ、CPU・メモリ・ファイルシステムの分離境界になります。

        

        

          
ライフサイクルActive / Idle / Stopped

          
セッションの3つの状態。処理中がActive、応答を返して待機中がIdle、アイドル時間の超過や上限到達でStoppedになります。StoppedになったmicroVMは破棄され、メモリは消去されます。

        

        

          
実行ロールexecution role

          
セッション内のエージェントがAWSリソースへアクセスする際に使うIAMロール。このロールの権限範囲が、そのままエージェントができることの範囲になります。

        

        

          
コールドスタートcold start

          
新しいセッションでmicroVMを起動する際に生じる、初回応答までの待ち時間。セッションが続いている間の呼び出しでは発生しません。

        

        

          
A2AAgent2Agent

          
異なる基盤で動くエージェント同士が通信するためのプロトコル。AgentCore RuntimeはMCPとあわせてA2Aへの対応が公式に案内されており、エージェントを「呼ばれる側」として公開できます。

        

        

          
Gateway / MemoryAgentCore family

          
AgentCoreの兄弟サービス。Gatewayは既存のAPIやLambda関数をMCPツールとして公開する橋渡し、Memoryはセッションを越えて残す短期・長期の記憶を担います。Runtimeと組み合わせて使います。
