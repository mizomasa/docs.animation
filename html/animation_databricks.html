Databricksの仕組みとエージェントI/O

Databricksは、データレイクとデータウェアハウスを1つに統合した「レイクハウス」のプラットフォームです。 このページでは、そもそもDatabricksが何で、業務DBやDWHと何が違うのかという序盤から、データの登録側・読み出し側の設計と実装パターン、 そしてAIエージェントからDatabricksへ読み書きするための接続・権限・安全設計までを、アニメーションと文章でたどります。

概要

Databricksは、クラウドのオブジェクトストレージに置いたデータを、データウェアハウス並みの信頼性とSQLで扱えるようにした統合データ基盤です。

データレイクの「何でも置けるが信頼性が低い」と、DWHの「信頼できるが閉じている・高い」という弱点を同時に解消するために、レイクハウスという形で生まれました。

取り込みから加工、BI、機械学習、そしてAIエージェントの読み書きまでが、Unity Catalogの権限管理のもとで同じデータに対して行えます。

背景

Databricksが生まれた背景 — 置き場が分かれていた時代

業務DB・データレイク・DWHの併存とサイロ化

組織のデータは、長い間3つの置き場に分かれていました。日々の業務を回す業務データベース（RDB）、とにかく安く大量に貯めるためのデータレイク、そして分析専用に整えられたデータウェアハウス（DWH）です。分析をしたいだけなのに、業務DBからレイクへ、レイクからDWHへとデータを何度もコピーするパイプラインが育ち、コピーのたびに鮮度が落ち、定義がずれ、障害点が増えていきました。同じ「売上」という数字が置き場ごとに微妙に違う、という事態も珍しくありませんでした。

データレイクの弱点 — 安いけれど「沼」になる

データレイクは、構造化データも画像やログのような非構造化データも、ファイルのまま安く置けるのが強みです。しかしファイルの寄せ集めには、書き込みの原子性を保証するトランザクションがありません。書き込みの途中で失敗すれば中途半端なファイルが残り、誰かが書いている最中に読めば壊れた結果が返ります。スキーマ（列の定義）も強制されないため、気づかないうちに形式の違うデータが混ざり、やがて誰も中身を信用できない「データの沼（データスワンプ）」と化すのが、レイクの典型的な末路でした。

DWHの弱点 — 信頼できるが、閉じていて高い

一方のDWHは、スキーマとトランザクションが厳格で、SQLによる集計は高速で信頼できます。その代わり、取り込めるのは整った構造化データが中心で、画像・音声・自由なテキストといった機械学習の材料は置きにくい。ストレージとコンピュートが一体の製品が多く、データを貯めるほど、使っていない時間も含めて費用が膨らみます。MLの学習ではDWHからデータを引き出して別の場所で処理することになり、結局またコピーが生まれます。

レイクハウスという答え

レイクハウスは、この2つを「ストレージはレイクのまま開いておき、その上にDWHの性質を載せる」ことで統合する考え方です。データ自体はクラウドのオブジェクトストレージにオープンな形式で置き、その上にトランザクション管理の層（DatabricksではDelta Lake）を被せて、ACID、スキーマ管理、履歴（タイムトラベル）を持たせます。コンピュートはストレージから独立していて、SQLの集計、Sparkの加工、MLの学習、エージェントの読み書きが、コピーではない同じデータに対して、それぞれ最適なエンジンで動きます。DatabricksはApache Sparkの開発元が作った会社であり、このレイクハウスを製品として推し進めてきた中心的な存在です。

ないとどうなるか

統合基盤がなければ、データ基盤は「コピーの連鎖」であり続けます。分析のたびにETLを組み、鮮度と正しさの検証に追われ、AIエージェントにデータを読ませようとしても「どのコピーが正なのか」「誰に見せてよいデータか」を接続のたびに個別に解くことになります。レイクハウスの価値は、速さそのものよりも先に、データの置き場と統治を1か所に寄せられる点にあります。

読み物

        
仕組みを文章で読む — レイクハウスを支える4つの部品

        
アニメーションの流れを、部品ごとに分解して文章でも押さえておきます。

        
Delta Lake — ファイルの上に「テーブルらしさ」を載せる

        
Delta Lakeは、Parquetファイルの集まりの横に _delta_log という取引ログを置く、オープンなテーブル形式です。書き込みは「ファイルを追加し、ログにコミットを記録する」ことで初めて確定し、読み手はログが指すファイルの組だけを見ます。これにより、オブジェクトストレージの上でもACIDトランザクションが成り立ち、書き込みの途中失敗が中途半端な状態を残しません。過去のバージョンを指して読むタイムトラベル（VERSION AS OF / TIMESTAMP AS OF）や、間違えた書き込みを巻き戻す復旧も、この履歴があるからできます。書き込み時にはスキーマが検証され（スキーマ強制）、列の追加のような変更はスキーマ進化として明示的に許す設計です。DatabricksではDeltaがテーブルの既定の形式になっています。

        
コンピュートとストレージの分離

        
データの実体はクラウドのオブジェクトストレージ（S3、ADLS、GCS）にあり、Databricks側のコンピュートは「処理のときだけ存在する」存在です。SQLの集計にはSQLウェアハウス、重い加工にはSparkクラスタ、定型の実行にはジョブやサーバーレスコンピュート、という具合に、処理の性質ごとにエンジンと大きさを選んで起動し、終われば止めます。貯める量と処理の量が独立に伸縮するので、「データは増え続けるが、処理は夜間だけ」という運用でも、ストレージの費用とコンピュートの費用を別々に最適化できます。

        
Unity Catalog — 全体を統治する名簿と門番

        
Unity Catalogは、レイクハウス内のすべてのデータ資産を登録し、権限を一元管理する仕組みです。資産は カタログ.スキーマ.テーブル という3階層の名前で指し、テーブル以外にもビュー、ファイル置き場であるボリューム、モデル、そして後述する関数やMCPサービスまでが同じ枠組みの管理対象（セキュラブル）になります。権限はこの名簿に対して GRANT で与え、行フィルタや列マスクのような細かい制御もここで定義します。どのテーブルがどのテーブルから作られたかというリネージ（系譜）や、誰が何にアクセスしたかという監査ログもUnity Catalog側に集まります。「どのデータを、誰が、どこまで見てよいか」を接続ごとではなく名簿の側で決めるのが、エージェントにデータを読ませる時代に効いてくる設計です。

        
ワークスペースと実行環境 — 人とプログラムの入口

        
利用者や開発者はワークスペースという入口から入ります。探索や試行錯誤にはノートブック、SQLの編集とダッシュボードにはSQLエディタとSQLウェアハウス、定期実行にはジョブ（Lakeflow Jobs）、宣言的なパイプライン構築にはSpark Declarative Pipelines（旧称Delta Live Tables）といった道具が並びます。どれを使っても、読み書きの先にあるのは同じDeltaテーブルとUnity Catalogの権限です。入口が違っても統治が一貫する、というのがレイクハウスの使い方の芯になります。

      


      
      

        
設計と実装 — 登録する側

        
登録する側の設計・実装 — 取り込みとメダリオン

        
取り込みパターン — バッチとストリーミング

        
Bronzeへの取り込みは、大きく分けて「ファイルを着地させてから取り込む」形と「流れてくるデータをそのまま受ける」形があります。ファイルの着地には、SaaSや業務DBから定期的に同期するマネージドな取り込み（Lakeflow Connect）や、単にオブジェクトストレージへファイルを置く運用が使われます。着地したファイルの取り込みでは、SQLの COPY INTO が素直な選択肢で、取り込み済みファイルを内部で記録するため、同じコマンドを再実行しても二重に取り込まれません。継続的にファイルが増えるなら Auto Loader（Sparkの cloudFiles）が向いていて、新着ファイルの検出とスキーマの保管場所（schemaLocation）を指定して、ストリーミングとして少しずつ流し込めます。Kafka等からイベントが直接流れてくる場合は、Structured Streamingで受けてDeltaへ書き続けます。

        

          

            
Python（PySpark）— Auto LoaderでBronzeへ流し込むイメージ

            
# 着地したJSONファイルを、新着分だけBronzeテーブルへ
raw = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "<スキーマ保管場所>")
    .load("<着地先のパス>"))

(raw.writeStream
    .format("delta")
    .option("checkpointLocation", "<チェックポイント>")
    .table("catalog.bronze.events"))

          

          
Auto Loaderは「どのファイルまで処理したか」をチェックポイントで覚えるため、再起動しても続きから処理できます。

        

        

          

            
SQL — COPY INTOによるバッチ取り込み

            
-- 取り込み済みのファイルは自動でスキップされる（冪等）
COPY INTO catalog.bronze.events
FROM '<着地先のパス>'
FILEFORMAT = JSON
COPY_OPTIONS ('mergeSchema' = 'true');

          

        

        
メダリオン設計 — 層ごとに「してよいこと」を決める

        
Bronzeは「生のまま」が原則です。ソースの構造を変えず、取り込み時刻やファイル名のようなメタデータを添えて、追記中心に保持します。あとから加工ルールが間違っていたと分かっても、Bronzeから作り直せることがこの層の存在意義です。Silverでは、型の整形、重複の排除、欠損の扱い、コード値の統一といった「データとしての正しさ」を入れ、エンティティ（顧客、注文、商品）ごとの信頼できる明細を作ります。Goldは利用用途の側に寄せ、ダッシュボード向けの集計、MLの特徴量、エージェントが読むためのビューなど、用途ごとに最適化した形で置きます。層を分けることで、「生データに触ってよい人」と「業務利用だけの人」で権限も自然に分けられます。

        
書き込みの作法 — MERGE、冪等性、スキーマ進化

        
SilverやGoldへの反映では、MERGE によるupsertが中心になります。キーで突き合わせ、あれば更新、なければ挿入、という処理を1つのトランザクションで確定させるため、ジョブが途中で落ちて再実行しても、同じ入力からは同じ結果になる（冪等である）ように設計できます。差分だけを渡す設計にすれば、再実行のコストも抑えられます。スキーマの変更は、列の追加のような後方互換なものはスキーマ進化で取り込みつつ、型の変更のような破壊的なものは新しいテーブルやバージョンとして扱うのが無難です。物理配置については、従来のパーティション分割に代わり、Databricksではリキッドクラスタリング（CLUSTER BY）が新しいテーブルの推奨とされており、よく使う絞り込み列を指定しておくと、読み取り時のファイルスキップが効くようになります。

        

          

            
SQL — MERGEによるSilverへのupsert

            
MERGE INTO catalog.silver.customers AS t
USING updates AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

          

          
「updates」は検証済みの差分だけを入れたステージング（作業用テーブル）を指す想定です。検証前のデータを直接MERGEしないのが、後述するエージェントの書き込みでも同じ作法になります。

        

      


      
      

        
設計と実装 — 読み出す側

        
読み出す側の設計・実装 — 「読ませる範囲」を設計する

        
基本の読み出し — SQLウェアハウスと各種コネクタ

        
外のプログラムから読む場合の主役はSQLウェアハウスです。JDBC/ODBCドライバを使えばBIツールや既存アプリから通常のSQLで引けますし、Pythonなら公式のDatabricks SQLコネクタで、接続してカーソルで実行する、DB-API風の書き方ができます。HTTPで叩きたい場合は、後述するSQL Statement Execution APIがRESTの入口になります。いずれの経路でも、実行はUnity Catalogの権限のもとで行われ、「接続できたこと」と「読めること」は別々に管理されます。

        

          

            
Python — Databricks SQLコネクタで読むイメージ

            
from databricks import sql

with sql.connect(
    server_hostname="<ワークスペースのホスト名>",
    http_path="<SQLウェアハウスのHTTPパス>",
    access_token="<トークン>",
) as conn:
    with conn.cursor() as cur:
        cur.execute(
            "SELECT product, amount FROM catalog.gold.daily_sales"
            " WHERE day = '2026-11-01' ORDER BY amount DESC LIMIT 5")
        rows = cur.fetchall()

          

          
トークンはコードに直書きせず、環境変数やシークレット管理から渡すのが前提です。

        

        
ビューと権限で「読ませる範囲」を切る

        
読み手に生のテーブルをそのまま見せるのではなく、用途に合わせたビューを公開面にするのが設計の基本です。ビュー側で、必要な列だけに絞る、個人情報を含む列を落とす、期間や区分で範囲を絞る、といった加工をしておけば、権限はビューに対する SELECT だけを与えればよくなります。行フィルタや列マスクをUnity Catalog側で定義すれば、同じテーブルでも見る人によって行や列の見え方が変わる、という制御も可能です。「何を読ませるか」は接続の作り方ではなく、名簿とビューの設計で決める、というのがレイクハウスの読み出しの考え方です。

        
組織の外へ渡す — Delta Sharing

        
データを他の組織や他のプラットフォームへ渡す場合は、ファイルを送るのではなく、Delta Sharingというオープンプロトコルで「共有」を作る方法があります。共有するテーブルやビューを指定し、受け手（レシピエント）にアクセス権を与えると、受け手は自分の環境から、権限の範囲内で最新のデータを直接読めます。コピーを渡さないので、鮮度の問題や「渡した後の管理不能」が起きにくく、アクセスの記録も共有元の側に残ります。

設計と実装 — エージェントI/O

        
エージェントI/Oの設計・実装パターン

        
接続手段の選び方 — 「何をさせたいか」で決める

        
エージェントからDatabricksへ届く経路は複数あり、用途で使い分けます。自然言語の質問に答えさせたいなら Genie が向いています。Genieは、対象のテーブルや指標の定義、例示を与えた空間（スペース）に対して自然言語で問い合わせると、SQLを生成して実行し、根拠とともに答えを返す仕組みで、エージェントからはGenie向けのマネージドMCPサーバーや会話API経由で呼びます。決まった形の処理をツールとして切り出したいなら、SQLやPythonで書いた Unity Catalog関数 をツール化する方法があり、関数はそのままMCPサーバーとして公開もでき、PythonからはUCFunctionToolkitでエージェントのツールに変換できます。文書の検索（RAG）には、Deltaテーブルから埋め込みインデックスを作るベクトル検索（AI Search）が使え、インデックスはテーブルの変更に追随して同期されます。自由なSQLを実行させたい場合は、Databricks SQL向けのマネージドMCPサーバーか、RESTのSQL Statement Execution APIを直接叩く形になります。公式ドキュメントでは、これらのワークスペース向けMCPエンドポイントはパブリックプレビューと案内されており（Genie等の提供形態は変わりやすいため、導入時に最新の公式ドキュメントで確認するのが確実です）。

Python — SQL Statement Execution APIをSDKから叩くイメージ

            
from databricks.sdk import WorkspaceClient

w = WorkspaceClient()  # 認証情報は環境変数などから解決される
resp = w.statement_execution.execute_statement(
    warehouse_id="<SQLウェアハウスのID>",
    catalog="catalog", schema="gold",
    statement="SELECT product, amount FROM daily_sales"
              " ORDER BY amount DESC LIMIT 5",
    wait_timeout="30s")  # 同期で待つ上限。超えたらIDでポーリング
rows = resp.result.data_array

          

          
Statement Execution APIは「SQLを投げて結果をJSONで受け取る」RESTの入口です。長いクエリは非同期にして、ステートメントIDで結果を取りに行く形にできます。

認証 — エージェントの「身分証」をどう持たせるか

        
エージェントの接続では、人のアカウントを借りるのではなく、サービスプリンシパルという機械用のアカウントを用意するのが基本です。認証はOAuthのマシン間（M2M）フローを用い、クライアントIDとシークレットから短命なアクセストークンを取得して使います。個人アクセストークン（PAT）は手軽な反面、個人に紐づき、失効や棚卸しの管理が曖昧になりやすいため、本番のエージェントではOAuthへの移行が推奨される、というのが公式の案内です。シークレットはコードやプロンプトに含めず、シークレット管理の仕組みから実行時に渡します。

        
権限設計 — 最小権限と「公開面」の分離

        
権限はサービスプリンシパルに対して、必要最小限だけを与えます。読み取りは、生テーブルではなく用途別のビューやUC関数への権限に絞るのが要点で、これにより「エージェントが見てよい範囲」は、エージェント側のプロンプトではなくUnity Catalog側の定義で決まります。プロンプトインジェクションでエージェントが想定外の指示に従ってしまっても、権限のないデータには原理的に届きません。書き込みはさらに一段厳しくし、専用のステージングテーブルへの書き込みだけを許可して、本テーブルへの反映は検証を挟んだ別工程（MERGE）にするのが安全な型です。

        
安全性 — 読み取り専用から始める

        
導入の順序としては、まず読み取り専用で始め、監査ログで「エージェントが実際に何を読んだか」を観測できるようにしてから、書き込みを段階的に開けるのが堅実です。Unity Catalogの監査ログには、誰（どのサービスプリンシパル）が、どの資産に、いつアクセスしたかが残るため、事後の検証が可能です。コスト面では、エージェントのクエリは暴走すると大きなスキャンになり得るので、SQLウェアハウスのサイズや自動停止、クエリの行数・時間の上限を設計に含めます。「賢く動くこと」と「暴走しても被害が小さいこと」は別の設計であり、後者は権限と上限で担保します。

      


      
      

        
強みと弱み

        
Databricksの良い点と弱点

        
良い点：置き場と統治が1か所に寄る

        
最大の強みは、データのコピーを減らし、権限・リネージ・監査をUnity Catalogに一元化できることです。BIでもMLでもエージェントでも、参照する先が同じで、見てよい範囲の定義も同じ。この一貫性が、データ基盤の運用コストと、AI活用の際の「出してよいデータか」という判断コストを下げます。Delta Lakeがオープンな形式であることも大きく、データ自体は特定ベンダーの専有形式に閉じ込められません。

        
弱点：コスト管理が設計問題になる

        
コンピュートは使った分だけ課金される従量制が基本で、起動しっぱなしのクラスタ、大きすぎるSQLウェアハウス、無計画な全件スキャンは、そのまま請求に跳ねます。安く済ませるには、自動停止の設定、ジョブ用の使い捨てコンピュート、サーバーレスの活用といった「止める設計」が要ります。統合基盤の便利さと、コストの見通しの難しさは表裏一体です。

        
弱点：学習コストと概念の多さ

        
Spark、Delta Lake、Unity Catalog、各種の実行環境と、押さえるべき概念は少なくありません。特に、コンピュートの種類の使い分けや、Deltaの物理最適化（ファイルサイズ、クラスタリング、VACUUM等の保守）は、効果が大きい分だけ運用知識を要求します。小さく始めて、必要な部分から型を固める進め方が現実的です。

        
注意点：ベンダー依存と守備範囲

        
Delta Lake自体はオープンでも、Unity Catalogによる統治や各種マネージド機能はDatabricksのプラットフォームに依存します。また、レイクハウスは分析とAIのための基盤であり、行単位の高速なOLTPは守備範囲の外です（その領域はLakebaseのような別製品が担います）。「何でもDatabricksで」ではなく、業務DBや他の基盤との役割分担を前提に置くことが、導入の成否を分けます。

      


      
      

        
まとめ

        
まとめ

        
Databricksは、データレイクの開放性とDWHの信頼性を、Delta LakeとUnity Catalogで束ねたレイクハウスのプラットフォームです。設計の芯は3つあります。データはBronze・Silver・Goldと段階を踏んで磨くこと。読み書きの範囲は接続方法ではなく名簿とビューと権限で決めること。そしてエージェントのような新しい読み手・書き手に対しても、サービスプリンシパルと最小権限という、従来と同じ原則で向き合うことです。エージェントI/Oは特別な魔法ではなく、「統治されたデータ基盤に、機械のアカウントで、道具経由で触る」という、基盤側の設計の延長にあります。

      


      
      

        GLOSSARY
        
用語解説

      

      

        

          
レイクハウスlakehouse

          
データレイクとデータウェアハウスの長所を組み合わせた基盤の考え方。オープンな形式でオブジェクトストレージに置いたデータに、トランザクションやスキーマ管理といったDWHの性質を載せます。

        

        

          
Delta Lake

          
Parquetファイルと取引ログ（_delta_log）で構成されるオープンなテーブル形式。ACIDトランザクション、タイムトラベル、スキーマ強制と進化、MERGEを提供します。Databricksではテーブルの既定形式です。

        

        

          
Unity Catalog

          
データ資産の名簿と権限管理の仕組み。カタログ.スキーマ.テーブルという3階層の名前で資産を指し、GRANTによる権限、行フィルタ・列マスク、リネージ、監査ログを担います。

        

        

          
メダリオンアーキテクチャmedallion

          
データをBronze（生）、Silver（整形・検証済み）、Gold（用途別に集計）の3層で整理する設計パターン。層を進むごとにデータの品質と業務への近さが上がります。

        

        

          
Auto LoadercloudFiles

          
着地したファイルを増分で取り込む仕組み。新着ファイルの検出とスキーマの管理を担い、Structured StreamingとしてBronzeへ流し込む使い方をします。

        

        

          
SQLウェアハウスSQL warehouse

          
SQLの実行に特化したコンピュート。BIツールや外部プログラムからのクエリを受け、サーバーレス型も選べます。JDBC/ODBCや各種APIの接続先になります。

        

        

          
Genie

          
自然言語でデータに問い合わせる機能。対象テーブルや指標の定義を与えた空間に対して質問すると、SQLを生成・実行して答えを返します。エージェント向けのMCPサーバーも提供されています。

        

        

          
サービスプリンシパルservice principal

          
プログラムやエージェントが使う機械用のアカウント。OAuthのマシン間認証でトークンを取得し、この主体に対してUnity Catalogの権限を与えます。

        

        

          
Delta Sharing

          
データをコピーせずに、組織やプラットフォームを越えて共有するためのオープンプロトコル。共有元が指定した範囲を、受け手が自分の環境から直接読みます。

        

        

          
Lakebase

          
Databricksプラットフォーム内のマネージドなPostgres。Unity Catalogのデータを同期して低レイテンシに読ませたり、エージェントの状態保存に使ったりと、OLTP寄りの置き場を担います。
