Strands Agentsの仕組み

Strands Agentsは、AWSが公開したオープンソースのAIエージェントSDKです。設計思想はモデル駆動（model-driven）—— エージェントとは「モデル＋ツール＋システムプロンプト」という最小構成であり、手順（フロー）は人が設計せず、モデルの推論に委ねる、という考え方です。 名前はDNAの二重らせんに由来し、モデルとツールという2本の「strand（鎖）」をつなぐもの、と公式ブログで説明されています。 まずエージェントループを8ステップで再生し、そのあと中身・他フレームワークとの違い・リスクを順に見ていきます。

概要

Strands Agentsは、AWSが公開したオープンソースのAIエージェントSDKで、エージェントを「モデル＋ツール＋システムプロンプト」の最小構成で作ります。

手順を開発者がフローとして設計する従来のフレームワークでは、想定外への対応や変更のたびの書き直しが重くなるため、手順そのものをモデルの推論に委ねる発想で生まれました。

書くコードが数行から始められるほど少なく、モデルが賢くなればエージェントの段取りまで良くなることが期待できます。

背景

Strands Agentsが生まれた背景 — フローを書くことの重さ

エージェント開発は「部品をつなぐ」作業だった

LLMを使ったアプリケーションの開発は、モデル、プロンプト、ツールといった部品を用意し、それらをつなぐ流れを開発者が設計する進め方が中心でした。部品の配線や状態の管理に書くコードは多く、エージェントらしい振る舞いを作る前に、土台の組み立てで手間がかかる構造になっていました。

部品自体は揃っていても、「どういう順番で、何を根拠に次を決めるか」という流れの設計が、開発者の側に残り続けていたのです。

手順を固定すると、想定外に弱い

流れを先に固定する設計では、分岐はすべて事前に書いておく必要があります。想定していなかった状況では処理が止まりやすく、要件が変わるたびに流れ全体を設計し直すことになります。タスクの内容が読めない仕事ほど、この弱さが表に出ます。

さらに、流れを固定する設計は、モデルの進化と相性がよくありません。モデルが賢くなっても、決められた分岐の中しか動けないため、段取りの改善は人の書き直しを待つことになります。

モデル側の能力が上がってきた

一方で、モデル自体の計画や推論、ツール使用の能力は上がり続けています。タスクを手順に分解し、結果を見て次を決めるという働きを、モデルがその場で担える場面が広がりました。ならば手順の設計を開発者からモデルへ移し、土台は薄く保つ、という発想が成立するようになります。

公式ブログでも、複雑なワークフローを定義させるフレームワークと比べて、モデルの計画・推論・ツール使用の能力をそのまま活かせることが、この方式を採った理由として挙げられています。

ないとどうなるか

モデル駆動の選択肢がなければ、開発者はエージェントごとに流れを書き続けます。モデルが代替わりして賢くなっても、段取りの良し悪しは固定された流れの範囲にとどまり、進化の恩恵を受けきれません。Strands Agentsは、その配線の重さを引き受ける代わりに、判断をモデルへ渡すという設計の転換だと言えます。

手順の設計を人が担い続ける限り、エージェント開発の中心は「タスクを解くこと」ではなく「流れを組むこと」に残り続けます。

STEP 1 / 8

          
エージェントは「3点セット」で作る

          

        

      


      
      

        
読み物

        
エージェントループを文章で読む — 委ねる範囲と、残る土台

        
アニメーションで再生した8ステップを、文章でもたどっておきます。

        
3点セットを用意して、文字列で呼び出す

        
開発者が用意するのは、モデルとツールとシステムプロンプトの3つです。Agentを作り、タスクを文字列で渡して呼び出すと、エージェントが動き始めます。手順を指示するコードはどこにもなく、呼び出しの形は通常の関数と変わりません。

        
システムプロンプトには役割や振る舞いを書き、ツールには実行させたい操作を持たせます。手順ではなく、材料と方針を渡すことが、この段階の仕事です。

        
ループの中で起きていること

        
呼び出されると、ハーネスが会話の履歴とツールの情報をモデルへ送ります。モデルは履歴を読んで次の一手を決め、ツールを使いたい場合は「このツールをこの引数で」という要求を返し、不要なら最終回答の文章を返します。ツール要求が来た場合、ハーネスがそのツールを実際に実行し、結果を履歴へ追加して、もう一度モデルを呼びます。この往復がエージェントループです。

        
天気の例では、まず天気ツールの呼び出しが返り、実行結果を見たモデルが「雨だから在庫も確認する」と判断して、次に在庫ツールを呼びます。この分岐はコードに書かれていたのではなく、モデルが結果を読んでその場で決めたものです。

        
履歴には、利用者の依頼、モデルの応答、ツールの実行結果が積み上がっていきます。モデルは毎回この履歴全体を読んで判断するため、前の結果を踏まえた軌道修正が可能になります。

        
ツールはどうやって生まれるか

        
ツールは、Pythonの関数に @tool を付けることで作られます。関数のdocstringがツールの説明文になり、型ヒントが引数のスキーマになります。モデルはこの説明文を読んで、いつ、どういうときにそのツールを呼ぶべきかを判断します。また、MCPサーバーに接続して外部のツールをそのまま取り込むこともでき、自作のツールと混ぜて使えます。

        
裏を返せば、説明文の書き方がそのままエージェントの判断材料になります。何をするツールなのか、いつ使うべきかが曖昧な説明では、モデルも正しく選びにくくなります。

        
終わり方と、広げ方

        
ループは、モデルがツール要求を含まない文章を返した時点で終わります。その文章が、呼び出し側への最終回答です。1体で足りなくなった場合は、別のエージェント自体をツールとして登録する Agents as Tools から始め、必要に応じてSwarmやGraph、Workflowといったマルチエージェントの形へ広げていきます。

        
この育て方でも、進み方を誰が決めるかは段階ごとに変わります。モデルに任せる範囲と、開発者が固定する範囲の配分を、設計として選んでいくことになります。

      


      
      

        SECTION 2
        
画面でこう見える — 開発者の書くコード

        
開発者の視点では、Strandsのコードは驚くほど短くなります。エージェントを作って、文字列で呼び出す。ループを回す処理はコードのどこにも現れません。

      

      

        
agent.py — 最小のエージェント（Python）

        
from strands import Agent

# モデル（既定は Amazon Bedrock）＋ツール＋プロンプトを用意するだけ
agent = Agent(
    tools=[get_weather, check_stock],
    system_prompt="あなたは店舗スタッフの助手です",
)

# あとは文字列で呼び出す。ループはSDKの中で回る
result = agent("明日の東京の天気を調べて。雨なら傘の在庫も確認して")
print(result)

      

      
公式ドキュメントのクイックスタートも、同様に Agent() を作って文字列で呼び出す数行から始まります。

      

        

          
ツールは「ふつうの関数」 @tool

          
Python関数に @tool デコレータを付けるだけで、そのままツールになります。関数のdocstringがツールの説明文に、型ヒントが引数のスキーマになり、モデルはそれを読んで「いつ・何を渡して呼ぶか」を判断します。説明文の書き方そのものが、エージェントの挙動を左右します。

          
@tool
def get_weather(city: str) -> str:
　"""指定した都市の天気を返します"""
　...

        

        

          
定義済みツールとMCP tools

          
別パッケージ strands-agents-tools には、ファイル操作・HTTPリクエスト・AWSのAPI操作など20以上の定義済みツールが用意されています（公式ブログ）。さらに MCPClient でMCPサーバーに接続すれば、公開されているMCPサーバーのツールをそのまま道具として取り込めます。自作ツールとMCPツールを混ぜて使うこともできます。

        

      


      
      

        SECTION 3
        
実際の中身のフロー — 4つの構成要素

        
エージェントの中身は、開発者が渡す3点と、それを回すループの、合わせて4要素です。役割分担がはっきりしているのが特徴です。

      

      

        

          
① モデル

          
推論とツール使用ができるLLMです。タスクの分解、次に呼ぶツールの選択、結果の解釈、終了の判断まで、「考える」部分はすべてモデルが担います。既定はAmazon Bedrock経由のモデルです。

        

        

          
② ツール

          
エージェントの「手足」です。@tool を付けた自作関数、定義済みツール、MCPサーバーのツール、さらには別のエージェント自体もツールとして渡せます。実行そのものは通常のプログラムとして行われます。

        

        

          
③ システムプロンプト

          
エージェントの役割と振る舞いを決める指示文です。モデル駆動では手順をコードで固定しない分、この指示文とツールの説明文が「設計」の中心になります。

        

        

          
④ ループ（ハーネス）

          
会話履歴を保持し、「モデルを呼ぶ→ツール実行→結果を返す」を繰り返す土台です。履歴の管理、エラーの扱い、ライフサイクルのフック（モデル呼び出しやツール実行の前後に処理を挟む仕組み）はここが担います。

        

      


      

        

          
モデルは差し替えられる model providers

          
既定はAmazon Bedrockですが、SDKはモデルに依存しない設計で、プロバイダーを差し替えられます。公式ドキュメント・PyPIの説明では、次のような組み込みプロバイダーが挙げられています。

          

            Amazon Bedrock（既定）
            Anthropic
            OpenAI
            Gemini
            Ollama（ローカル）
            Llama API
            Mistral
            Cohere
            SageMaker
            LiteLLM 経由
            カスタム
          

          
つまり「AWSのSDKだが、頭脳はAWSのモデルでなくてもよい」作りです。ローカル開発ではOllama、本番ではBedrock、といった切り替えができます。

        

        

          
MCPサーバーとつながる MCPClient

          
StrandsはMCP（Model Context Protocol）のクライアントとして動き、MCPサーバーに接続してそのツール一覧を取り込みます。

          
MCPClient( …サーバーへの接続… )
with client:
　agent = Agent(tools=client.list_tools_sync())

          
道具の供給元を「自分のコード」から「外部のサーバー」へ広げられるため、公開MCPサーバーの資産をそのまま使えます。自作の @tool と併用も可能です。

        

      


      

        
マルチエージェント — 4つのパターン

        
1つのエージェントで足りなくなったら、複数を組み合わせます。公式ドキュメントでは、違いは「実行の進み方を誰が決めるか」にあると整理されています。単一エージェントから少しずつ育てるのが推奨の順序です。

      

      

        

          
Agents as Tools

          
進み方：司令塔のモデルが決める

          
専門エージェントを、司令塔エージェントのツールとして登録する最小のパターン。司令塔が質問に応じて専門家を呼び、答えを回収して自分の文脈でまとめます。まずはここから、が公式の案内です。

          
司令塔Agent
　├─ tool: 天気Agent
　└─ tool: 在庫Agent

        

        

          
Swarm

          
進み方：エージェント同士が決める

          
専門エージェントのチームが、共有メモリとハンドオフ（引き継ぎ）で自律的に連携するパターン。固定の経路はなく、その場の判断で次を担当するエージェントが入れ替わります。自由な分、動きの予測は難しくなります。

          
調査 ⇄ 分析 ⇄ レビュー
（共有メモリ＋引き継ぎ）

        

        

          
Graph

          
進み方：開発者が辺を定義

          
エージェントをノード、遷移を辺とするグラフを開発者が定義します。無条件の辺は常に従い、条件付きの辺は条件を満たしたときだけ進むため、「レビューで差し戻し」のような循環や品質ゲートを表現できます。

          
調査 → 分析 → レビュー
　　　　　└ 差し戻し ┘

        

        

          
Workflow

          
進み方：開発者がコードで固定

          
タスクとその依存関係（DAG）を定義し、決まった順序で実行するパターン。依存しないタスクは自動で並列実行されます。決定的で再現性が高い反面、その場の判断による分岐はしません。

          
抽出 → 分析A ┐
　　 → 分析B ┘→ 報告

        Strands Agentsは、AWS Open Source Blogで2025年5月16日にオープンソースSDK（Apache-2.0）として発表され、2025年7月にバージョン1.0が公開されました（マルチエージェントの基本部品とA2Aプロトコル対応を含む）。Python SDKが先行し、TypeScript SDKも提供されています。
        公式ブログによれば、公開前からAWS社内で使われており、Amazon Q Developer、AWS Glue、VPC Reachability Analyzerの各チームが本番のエージェントに利用していると説明されています。
      


      
      

        SECTION 4
        
他のフレームワークとの違い — 「設計する」か「委ねる」か

        
LangChainに代表される「部品組み立て型」は、モデル・プロンプト・ツールといった部品を開発者がつなぎ、流れそのものを設計します。Strandsのモデル駆動は、その流れの設計をモデルに委ねる点が対照的です（このシリーズの「LangChainとAgent SDK」のページでいう「ループ内蔵型」と同系統で、その中でもモデルへの委任の度合いが高い設計です）。

      

      

        

          
            
観点部品組み立て型（LangChain的）モデル駆動（Strands Agents）

          
          
            

              流れの決め方
              開発者が鎖（チェーン）やグラフとして事前に設計する
              モデルが実行時に判断する。開発者は流れを書かない
            

            

              書くコード
              部品の配線・状態管理が中心で、どうしても多めになる
              モデル・ツール・プロンプトの指定が中心。数行から始められる
            

            

              モデルが賢くなると
              設計した流れはそのまま。恩恵は各部品の中の性能向上にとどまる
              手順の組み立てもモデル任せなので、モデルの進化がそのままエージェントの性能向上につながりやすい
            

            

              再現性
              流れが固定されている分、予測しやすく再現性が高い
              実行ごとに経路が変わりうる。同じ依頼でも結果が揺れることがある
            

            

              想定外への対応
              分岐を先に書いておく必要がある。想定外は止まりやすい
              モデルがその場で対処できる。ただし対処の仕方自体もモデルの判断に依存する
            

            

              向く場面
              手順が決まっていて、監査や再現性が要る業務フロー
              手順を事前に固定しにくい、探索的・対話的なタスク
            

          
        

      

      

        

          
モデル駆動の利点

          
コードが少なく、作り始めるまでが速いのが第一です。加えて、手順の組み立てをモデルに任せるため、モデルが世代交代で賢くなると、コードを直さなくてもエージェントの段取りまで良くなる可能性があります。AWSがこの方式を採った理由として、公式ブログでは「複雑なワークフローを定義させるフレームワークと比べ、モデルの計画・推論・ツール使用の能力をそのまま活かせる」ことが挙げられています。

        

        

          
モデル駆動の弱点

          
挙動がモデル依存になるため、再現性と予測可能性は下がります。モデルを差し替えれば段取りも変わりえますし、「必ずこの順序で」「ここで必ず止める」といった統制は、ループ側の仕組み（フックやGraph/Workflowのような決定的パターン）で別途かける必要があります。コストも、ループの周数に比例して読みにくくなります（セクション5）。

        

      


      
      

        SECTION 5
        
リスクと注意点 — 任せる範囲をどう絞るか

        
モデル駆動は「委ねる」設計なので、歯止めは自分で用意するのが前提です。代表的なリスクと、SDKや周辺で用意されている対策を並べます。

      

      

        

          
ループの暴走とコスト

          
終了判定はモデルの出力頼みです。モデルが「まだ終わっていない」と判断し続ければ、ループは回り続け、その分だけモデル呼び出しとツール実行のコストが積み上がります。

          
対策：最大ステップ数・タイムアウト・トークン予算といった上限を外側で決め、結果オブジェクトのメトリクスやログで消費を監視します。

        

        

          
ツールの権限管理

          
シェル実行やファイル操作のツールは、実質的に「プログラムの実行権限」をモデルに渡すのと同じです。定義済みツールには強力なものも含まれるため、便利さと危険さは表裏一体です。

          
対策：最小権限が原則です。読み取り専用のツールから始め、認証情報はツール側に持たせすぎず、実行環境はサンドボックスや専用環境に隔離します。

        

        

          
プロンプトインジェクション

          
ツールが返した外部コンテンツ（Webページや文書）に紛れた指示を、モデルが「次の命令」と誤認して従ってしまうリスクがあります。ツール結果はモデルの文脈にそのまま入るため、モデル駆動では特に意識が必要です。

          
対策：入力・出力の検査にはAmazon Bedrock Guardrailsとの連携が使えます（公式サイトでも導入事例として言及）。ツール実行の前後にフックで検査や記録を挟むことも有効です。

        

        

          
不可逆な操作と人の確認

          
送信・削除・課金のような取り消せない操作を、モデルの判断だけで実行させるのは危険です。モデル駆動のループには、標準では「人の承認待ち」という概念が薄くなりがちです。

          
対策：フックや割り込み（interrupt）の仕組みで、危険なツールの実行前にループを止めて人の承認を挟みます。公式サイトの事例でも、hooksとinterruptsで承認前にエージェントを停止させる運用が紹介されています。

        

      

      

        再現性はモデル依存、という前提で評価する。
        同じ入力でも、モデルの世代や設定が変われば段取りと結果は変わりえます。本番投入の前後では、決まったケース集で挙動を測る評価（Strandsには評価用の仕組みとしてStrands Evalsが用意されています）を回し、モデル差し替え時の「回帰」を確認するのが安全です。観測の面では、トレースやメトリクスを出す仕組み（OpenTelemetry連携など）も公式に案内されています。
      


      
      

        
強みと弱み

        
Strands Agentsの良い点と弱点

        
良い点：速く作れて、モデルの進化に乗れる

        
利点の中心は、作り始めるまでの速さです。用意するものが3点セットで済むため、数行から動くものが得られ、試行錯誤の周期を短くできます。手順の組み立てをモデルに委ねているので、モデルの世代交代で推論が賢くなれば、コードを直さなくてもエージェントの段取りまで良くなる可能性があります。モデル自体も差し替え可能で、既定のAmazon Bedrock以外を選ぶ余地が残されています。

        
弱点：再現性と統制は自分で足す

        
委ねる設計である以上、挙動はモデルに依存します。同じ依頼でも経路が変わりうるし、モデルを差し替えれば段取りも変わります。「必ずこの順序で実行する」「ここで必ず止める」といった統制は標準では薄く、フックで処理を挟んだり、GraphやWorkflowのような決定的なパターンを組み合わせたりして、外側から足す必要があります。コストもループの周数に比例するため、事前には読みにくい部類です。

        
上限の設定や実行の記録といった、ループの外側の備えも欠かせません。終了の判断自体が、モデルの出力に委ねられているためです。

        
弱点：ツールの説明文が、そのまま判断の質になる

        
モデルは、ツールの説明文と引数のスキーマだけを頼りに道具を選びます。説明が曖昧だったり、似たツールが並んでいたりすると、呼び出しの選択を誤ります。書くコードの量は減っても、ツールの説明文とシステムプロンプトを設計する手間は残り、その出来がエージェントの挙動を大きく左右します。

      


      
      

        GLOSSARY
        
用語解説

      

      

        

          
モデル駆動model-driven

          
エージェントの進み方（計画・手順・ツールの選択・終了判定）を、開発者がフローとして書くのではなく、モデルの推論に委ねる設計思想。Strands Agentsの中核の考え方です。

        

        

          
エージェントループagent loop

          
「モデルを呼ぶ→ツール実行の要否を見る→実行して結果を返す→またモデルを呼ぶ」という繰り返し。モデルがツール呼び出しを含まない最終回答を返すと終了します。

        

        

          
@tooltool decorator

          
Python関数に付けるデコレータ。これだけで関数がツール化され、docstringがツールの説明文、型ヒントが引数のスキーマになります。TypeScript版ではZodスキーマでツール定義を書きます。

        

        

          
ハーネスharness

          
モデルとツールのあいだでループを回す土台の部分。会話履歴の保持、ツール実行、継続・終了の管理、フックの提供などを担います。

        

        

          
フックhooks

          
モデル呼び出しやツール実行といったライフサイクルの節目に、自前の処理（ログ、検査、承認待ちなど）を差し込む仕組み。モデル駆動のループに統制を加える主な手段です。

        

        

          
MCPModel Context Protocol

          
ツールやデータを外部サーバーから供給するための共通規約。StrandsはMCPクライアントとしてサーバーに接続し、そのツールをエージェントの道具として使えます。

        

        

          
Agents as Tools

          
エージェントを別のエージェントのツールとして登録する、最も単純なマルチエージェントのパターン。司令塔が専門家エージェントを呼び分ける階層型の委任です。

        

        

          
Swarm / Graph / Workflow

          
マルチエージェントの進み方の違いを表す3パターン。Swarmはエージェント同士の自律的な引き継ぎ、Graphは開発者が定義したノードと辺（条件分岐あり）、Workflowは依存関係（DAG）による決定的な実行です。

        

        

          
ガードレールguardrails

          
入出力の内容を検査し、不適切な内容や想定外の指示を遮断・警告する仕組み。StrandsではAmazon Bedrock Guardrailsと連携させる使い方が公式に案内されています。

        

        

          
A2AAgent2Agent

          
異なる基盤で動くエージェント同士が通信するためのプロトコル。Strands Agents 1.0で対応が追加され、フレームワークをまたいだエージェント連携の道が開かれました。

        

      


      
      

        
まとめ

        
まとめ

        
Strands Agentsは、エージェントの設計を「流れを書くこと」から「材料を渡して判断を委ねること」へ移したSDKです。モデル、ツール、システムプロンプトの3点セットと、それを回すループだけで構成され、手順の組み立てはモデルの推論に任されます。その分、再現性の担保や統制、コストの読みは開発者側の設計に残ります。手順を固定しにくいタスクでは委ねる利点が大きく、手順の保証が要る場面では決定的な仕組みと組み合わせる、という使い分けが要点です。
