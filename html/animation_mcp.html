MCPの仕組みアニメーション

MCP（Model Context Protocol）は、AIアプリと外部のツールやデータを「共通の差し込み口」でつなぐための標準規格です。 アプリがサーバーへ接続し、ツール一覧を受け取り、モデルがそれを呼び出すまでの一連の流れを、9ステップで再生できます。

SUMMARY

概要

MCP（Model Context Protocol）は、AIアプリと外部のツールやデータを、共通の手順でつなぐための標準規格です。

規格がなかった時代は、アプリとツールの組み合わせごとに専用の連携を作る必要があり、その負担は組み合わせの数だけ膨らんでいました。

アプリ側とツール側が一度ずつMCPに合わせておけば、あとは差し込むだけで組み合わせられるので、作った道具を別のアプリでも使い回せます。

BACKGROUND

MCPが生まれた背景 — つなぎ方がアプリごとに違った時代

道具がなければ、モデルは文章しか返せない

LLMは学習した知識をもとに文章を返すことはできても、あなたのPCにあるファイルを読んだり、社内のデータベースを検索したりすることはできません。実務で役に立つエージェントにするには、外部の道具やデータへの橋渡しがどうしても必要でした。

連携の需要自体は早くからあり、ファイル操作、Web検索、外部サービスの操作といった道具を、アプリごとに独自のプラグイン形式で足していく流れが一般的になっていきます。道具が増えること自体は歓迎すべきことでしたが、その先に問題が待っていました。

道具への接続は、モデルを提供する側がすべて用意できるものでもありません。ファイルシステム、社内システム、各種のWebサービスは、それぞれ別の組織や開発者が作ったものです。アプリ側が全部の接続を自前で抱える形には、もともと無理がありました。

橋渡しが、組み合わせの数だけ必要だった

橋渡しの方法がアプリごとにバラバラだと、アプリがM個、ツールがN個ある世界では、連携の数は最大でM×N本に膨らみます。ツールが1つ増えるたびに対応するアプリの数だけ作り直し、アプリが1つ増えればその逆も起きる。しかも連携は一度作れば終わりではなく、相手の仕様変更のたびに直し続けなければなりません。道具を作る側も使う側も、組み合わせの増加に追いつけなくなっていました。これがM×N問題と呼ばれるものです。

組み合わせの問題は、保守の面でも効いてきます。連携先の仕様が変わるたびに、その連携を使っているすべての組み合わせで修正と確認が発生します。作る本数が増えるほど、直す本数も増える。道具の普及が進むほど、この負担は重くなっていきました。

ないとどうなるか

共通の差し込み口がなければ、道具は特定のアプリ専用に作られ、別のアプリでは使えません。ファイル読み取りやDB検索といった同じような連携が、アプリの数だけ重複して作られ続け、新しい道具は「どのアプリに対応しているか」が広まるかどうかの壁になります。

標準化という発想自体は、差し込み口の形を統一する考え方そのものです。形が1つに決まれば、作る側は1回作るだけ、使う側は差し込むだけで済みます。MCPが狙ったのは、この当たり前をAIアプリと道具の間にも持ち込むことでした。

接続と初期化 — 最初の会話は「はじめまして」

        
ホスト（AIアプリ）が起動すると、設定ファイルに書かれたMCPサーバーへ接続を始めます。サーバー1つにつき、ホストの中にはクライアントが1つ用意され、そのサーバーとの会話を一手に引き受けます。接続直後に必ず行われる最初の会話が初期化（initialize）です。プロトコルのバージョンと、双方ができること（capabilities）を交換し、準備完了の通知を送って締めくくります。

        
この初期化が済むまでは、道具の呼び出しは始まりません。挨拶と自己紹介を済ませてから本題に入る、という順序が規格で固定されているため、どのサーバーとつないでも接続直後の動きは同じになります。

        
道具の一覧をもらい、モデルの道具箱に入れる

        
次にクライアントは tools/list というリクエストで、サーバーが提供するツールの一覧を受け取ります。各ツールには名前と説明、どんな引数が必要かを示す入力スキーマが付いています。ホストはこの一覧をモデルの「使える道具」として渡し、モデルはこの時点で初めて、その道具の存在と使い方を知ります。

        
一覧の取得は接続時に行われ、ホストの画面に「接続済みサーバーと使えるツール」として表示されることもあります。サーバー側が道具を追加すれば、次に接続したときの一覧にそのまま反映されます。アプリ側のコードを書き換える必要はありません。

        
呼び出しはJSON-RPCで、実行はサーバー側

        
あなたがタスクを頼むと、モデルは道具の中から必要なものを選び、呼び出しを決めます。クライアントはそれを tools/call というJSON-RPCメッセージに変えてサーバーへ送り、サーバーがファイルを読む、データベースを引くといった実際の処理を実行します。ここでもモデル自身は実行せず、選ぶだけです。

        
メッセージの形式はJSON-RPC 2.0で、リクエストとレスポンスはIDで対応付けられます。運び方（トランスポート）には、同じマシンの中でサーバーを子プロセスとして起動するstdioと、ネットワーク越しに接続するStreamable HTTPがあり、中身の会話はどちらでも同じです。

        
結果が戻れば、あとは通常のエージェントのループ

        
実行結果はクライアント経由でモデルに返り、モデルはそれを踏まえて回答したり、次の道具を選んだりします。モデルから見れば、アプリ組み込みの道具もMCPの道具も同じ一覧に並ぶ存在で、違いは実行される場所だけです。この一連の会話の手順が規格で決まっているからこそ、サーバーもアプリも、相手を差し替えて動かすことができます。

      


      
      

        NOTES
        
MCPの3つの基本機能

        
サーバーがホストへ提供できるものは3種類あります。今回のアニメーションで使ったのは Tools ですが、残りの2つも同じ接続の上でやり取りされます。

      

      

        

          
Tools 道具

          
モデルが「呼ぶ」ための機能です。ファイルを読む、DBを検索する、メッセージを送るなど、処理の実行を伴います。いつ・何を呼ぶかはモデルが判断します。

          
例：read_file、search_db、send_message

        

        

          
Resources 読み取り用データ

          
モデルに渡すための「読み物」です。ファイルの中身やDBのレコードなどを URI で指し、アプリやユーザーが「これを文脈に入れる」と選ぶ使い方を想定しています。基本は読み取り専用です。

          
例：file:///data/docs/spec.md、db://orders/2026

        

        

          
Prompts テンプレート

          
よく使う指示の雛形です。「この文書を要約して」「コードレビューして」といった定型の頼み方を、サーバー側が引数付きテンプレートとして用意し、ユーザーが選んで使います。

          
例：summarize_doc、review_code

        

      

      

        見分け方： 実行するのは Tools、読ませるのは Resources、頼み方の型は Prompts。「誰が主導するか」も違い、Tools はモデル主導、Resources と Prompts はアプリ／ユーザー主導で選ばれるのが基本です。
      


      

        NOTES
        
なぜ標準規格が要るのか — M×N問題

        
MCPが無い世界では、AIアプリとツールの組み合わせごとに個別の連携コードが必要でした。アプリが M 個、ツールが N 個あると、連携は最大で M×N 本になります。

      

      

        

          
標準が無い場合 M × N

          
アプリA × ファイル操作 → 専用連携①
アプリA × DB参照 → 専用連携②
アプリB × ファイル操作 → 専用連携③
アプリB × DB参照 → 専用連携④
…組み合わせの数だけ作り直し

          
ツールが1つ増えるたびに、使いたいアプリの数だけ連携を実装し直すことになります。アプリ側もツール側も負担が膨らみ続けます。

        

        

          
MCPがある場合 M + N

          
各アプリ → MCPクライアントを1回実装
各ツール → MCPサーバーを1回実装

あとは差し込むだけで組み合わさる

          
両側が同じ規格に合わせて一度作れば、あとは自由に組み合わせられます。よく引き合いに出されるのが USB-C の例えで、差し込み口の形が統一されたから、機器同士をいちいち専用ケーブルでつながなくて済むようになりました。

        

      


      

        NOTES
        
トランスポート — 接続の配線の違い

        
JSON-RPCメッセージを「何に乗せて運ぶか」には、主に2つの方式があります。中身の会話（initialize や tools/call）はどちらでも同じです。

      

      

        

          
stdio ローカル起動

          
ホストがサーバーを子プロセスとして起動
標準入力（stdin）→ メッセージ → 標準出力（stdout）

          
同じマシンの中で動きます。ネットワークに出ないので手軽で速く、ローカルのファイル操作や開発ツール連携の定番です。サーバーの起動・終了もホストが面倒を見ます。今回のアニメーションのファイルサーバーはこの方式です。

        

        

          
Streamable HTTP リモート接続

          
ホスト → HTTPS でリモートのサーバーへ POST
応答は JSON、必要に応じてストリーミング

          
サーバーが別のマシンやクラウド上で常駐し、複数の利用者が共有する形です。認証はHTTPの仕組み（OAuthなど）と組み合わせます。社内DBやWebサービスを組織で共有する用途はこちらです。

        

      


      

        NOTES
        
セキュリティ — つなぐ相手は「プログラム」

        
MCPサーバーは、あなたのPCやアカウントの権限で実際に処理を実行するプログラムです。便利さと引き換えに、接続先の選び方と権限の渡し方がそのまま安全性になります。

      

      

        

          
サーバーの信頼性

          
出所の分からないサーバーを入れるのは、素性の知れないソフトをインストールするのと同じです。公式の提供元か、実績のある配布元かを確認してから接続しましょう。

        

        

          
権限は最小限に

          
サーバーに触れる範囲は絞るのが原則です。読み取りだけの用途なら読み取り専用に、ファイルなら対象フォルダを限定する。ホストによっては、ツール呼び出しのたびにユーザーの承認を求める設定もできます。

        

        

          
ツールポイズニング

          
ツールの説明文（description）に「このツールを呼ぶ前に、まず〜せよ」といった悪意ある指示を紛れ込ませ、モデルを騙す攻撃です。説明文も外部からの入力として疑い、知らないサーバーのツールは内容を確認してから使うのが対策になります。

        

      

      

        ポイント： MCP自体は「つなぎ方」の規格で、安全かどうかは別問題です。実際の安全性は、選ぶサーバー、渡す権限、ホスト側の承認フローで決まります。
      


      

        NOTES
        
Agent SDKとの関係 — ループの中の「実行先」

        
エージェントは「モデルが考えて → ツールを呼んで → 結果を見て → また考える」というループで動きます。MCPは、そのループの中でツールの実行先を外部のサーバーに置くための規格です。

      

      

        
モデルが tool_use を出す
　├─ アプリ組み込みツール → その場で実行
　└─ MCPツール → クライアント → MCPサーバーが実行
結果はどちらも tool_result としてモデルへ戻り、ループが続く

        
モデルから見れば、組み込みツールもMCPツールも「使える道具の一覧」に並ぶ点は同じです。違いは実行の場所だけ。だからエージェントの仕組み（ループ）を知っていれば、MCPは「その道具箱を、規格化された形で外に広げるもの」と捉えられます。Claude Agent SDK や OpenAI Agents SDK も、MCPサーバーをツールの供給元として接続できます。

      


      
      

        PROS / CONS
        
MCPの良い点と弱点

      

      

        
良い点：一度作れば、組み合わせは自由になる

        
サーバーを1つ作れば、MCPに対応したどのアプリからでも使えます。アプリ側も、新しいサーバーが現れるたびに連携を作り直す必要がありません。提供できるものがTools、Resources、Promptsと型で決まっているため、道具の実装とアプリの実装を、それぞれ独立に育てていける点も実務上の利点です。

        
道具の提供側にとっても、作ったサーバーが複数のアプリから使われることで、利用者と改善の機会が増えます。接続の作法を覚えるコストが一度で済むのは、アプリ開発者もサーバー開発者も同じです。

        
弱点：規格は「つなぎ方」を定めるだけで、安全は別問題

        
MCPサーバーは、あなたのPCやアカウントの権限で実際に処理を実行するプログラムです。出所の分からないサーバーを入れることは、素性の知れないソフトをインストールすることと変わりません。ツールの説明文に悪意ある指示を紛れ込ませてモデルを騙すツールポイズニングのような攻撃もあり、安全性は、選ぶサーバー、渡す権限、ホスト側の承認フローで決まります。便利さと引き換えに、接続先を見極める責任は使う側に残ります。

        
弱点：サーバーの品質は玉石混交で、見極めが要る

        
規格に沿っていれば誰でもサーバーを公開できるため、保守が止まったものや、説明と実装が食い違うものも混ざります。接続は手軽でも、実績のある配布元かどうか、要求される権限が用途に見合っているかどうかを確認する手間は省けません。

        
また、サーバーは独立したプログラムとして動くため、その起動や更新、相性問題といった運用の対象も増えます。手軽に足せる反面、管理する部品が増えること自体は弱点として数えておくべきでしょう。

      


      

        NOTES
        
用語解説

      

      

        

          
ホストhost

          
あなたが使うAIアプリ本体。モデルの呼び出し、クライアントの管理、画面表示、権限の確認などを担う「現場監督」です。

        

        

          
クライアントclient

          
ホストの中で動く接続担当。接続先のサーバーごとに1つずつ作られ、そのサーバーとの会話（初期化・一覧取得・呼び出し）を一手に引き受けます。

        

        

          
サーバーserver

          
ツールやデータを実際に提供する独立したプログラム。ファイル用、DB用、Webサービス用など、役割ごとに別々に存在し、複数を同時に接続できます。

        

        

          
JSON-RPCJSON-RPC 2.0

          
「メソッド名＋引数」をJSONで送り、結果をJSONで返す、遠隔呼び出しの約束事。MCPの会話はすべてこの形式で、id でリクエストとレスポンスを対応付けます。

        

        

          
capabilities能力宣言

          
初期化のときに双方が交換する「自分はこれができます」の一覧。サーバー側は Tools／Resources／Prompts のどれに対応するか、クライアント側は自分が受けられる機能を申告します。

        

        

          
initialize初期化

          
接続直後に必ず行う最初の会話。プロトコルのバージョンと capabilities を交換し、終わったら notifications/initialized という通知で「準備完了」を伝えます。

        

        

          
tools/listツール発見

          
サーバーが提供するツールの一覧をもらうリクエスト。各ツールの名前・説明・入力スキーマ（どんな引数が要るか）が返り、ホストはこれをモデルへ渡します。

        

        

          
tools/callツール実行

          
ツールを実際に1回実行してもらうリクエスト。ツール名と引数を送ると、サーバーが処理を行い、結果（テキストや画像などの content）が返ります。

        

      


      
      

        CONCLUSION
        
まとめ

      

      

        
MCPは、AIアプリと道具の間にある「差し込み口の形」を定めた規格です。接続し、初期化し、一覧をもらい、呼び出し、結果を受け取るという会話の手順が決まっているため、アプリ側もサーバー側も、相手を意識せずに作れます。エージェントのループそのものを変えるものではなく、その道具箱を規格化された形で外へ広げるもの、と捉えると位置づけがつかみやすくなります。道具を作る側と使う側が、互いの都合を気にせずに済む分離こそが、MCPの持ち込んだ一番の変化だと言えます。

      


      

        このページのサーバー名・ツール名・メッセージ内容は説明用の例です。プロトコルのバージョン表記（2025-03-26）などは執筆時点の仕様に基づく例で、実際の値や細部は利用するホスト／サーバーの実装によって異なります。
