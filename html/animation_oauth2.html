OAuth 2.0の仕組み — 「この鍵で、ここまで開けていいよ」

OAuth 2.0は「認証」ではなく 「認可」 の仕組みです。アプリにパスワードを渡すのではなく、あなたの代わりにデータへアクセスする許可 を与えます。その上に「身元確認」を載せたものがOIDCです。下のアニメーションで、現在の標準である 認可コードフロー＋PKCE を1ステップずつ追ってみましょう。例は「写真プリントアプリが、あなたのGoogleフォトの写真を使えるように連携する」場面です。

            アプリは「あなたのデータを使いたい側」、認可サーバーは「許可を出す側」、APIは「データを持つ側」です。OAuthの肝は、アプリにパスワードを渡さず、許可の範囲（scope）が書かれたアクセストークンだけを渡す点にあります。

            OAuth 2.0 と OIDC の違い

            OAuth 2.0OIDC
            目的認可 — アプリに、あなたの代わりにデータへアクセスする許可を与える認証 — あなたが誰かを、アプリに伝える
            一言で「この鍵で、ここまで開けていいよ」OAuthの上に作った「身元確認」の仕組み
            成果物アクセストークン（APIを呼ぶ鍵）IDトークン（誰がログインしたか）＋ アクセストークン
            例えホテルのキーカード（部屋に入れる範囲が決まっている）キーカード＋身分証（誰のカードかも分かる）

            OAuthは本来、認可のための仕組みです。その上に「ログインした人は誰か」を伝える仕組みを足したものがOIDCです。このページの主役はOAuthの「認可」の方です。

            なぜ「認可コード」を挟むのか

            • ブラウザのアドレスバーを経由する通信は漏れる前提で設計します。履歴やログ、拡張機能などから見えてしまう可能性があります。
            • そこで、まず「引換券（認可コード）」だけをブラウザ経由で渡し、本物のトークンはアプリと認可サーバーが直接やり取りする裏の通信（バックチャネル）で渡します。
            • 認可コード自体も、短命（通常10分以内）・1回限りで、漏れても被害を小さく抑えます。
            • さらにPKCEを重ねることで、コードを盗まれただけでは引き換えられないようにします（次のカード）。

            3種類のトークン — 宛先が違います

            OIDCまで含めると、トークンは3種類出てきます。混同しやすいのは「誰に向けたものか」がそれぞれ違う点です。

            トークン誰に向けたものか何に使うか
            IDトークンアプリ（クライアント）「誰がログインしたか」を知る（OIDCで発行される）
            アクセストークンAPI（リソースを持つサーバー）「この操作をしてよい」と示してAPIを呼ぶ — このページの主役
            リフレッシュトークン認可サーバー期限切れのアクセストークンを更新する
            注意： IDトークンを、APIを呼ぶための通行証として使ってはいけません。 IDトークンは「アプリに、誰がログインしたかを伝える」ためのもので、APIに見せるためのものではありません。ここを混同する設計は、よくある間違いです。

            PKCEが防ぐもの

            引換券（認可コード）自体が盗まれたら、攻撃者が自分でトークンに引き換えてしまうかもしれません。そこで PKCE（ピクシー） です。

            • ログイン開始時に、アプリが使い捨ての秘密 code_verifier を作る
            • そのハッシュ code_challenge だけを、最初に認可サーバーへ伝える
            • 引き換え時に、元の code_verifier を見せる
            • 認可サーバーが、ハッシュの一致を確認する

            たとえるなら、引換券を取りに行くとき、最初に「合言葉から作った指紋（元の合言葉には戻せない）」だけを預けておき、引き換えるときに「合言葉そのもの」を言うようなものです。指紋からは合言葉を推測できないので、引換券だけを盗んだ人は引き換えられません。

            PKCEはもともと、スマホアプリのような「秘密を安全に隠せないアプリ（パブリッククライアント）」のために作られました。現在では、OAuth 2.1（策定中の次期仕様）やMCPの認可仕様でも、認可コードフローではPKCEを使う前提になっています。

            stateの役割 — CSRF対策

            state は、別のログイン結果を無理やり送りつける攻撃（CSRF）を防ぐための値です。照合の流れはこうです。

            1. ログイン開始時、アプリが推測できないランダムな state を作り、保存しておく
            2. 認可サーバーは、受け取った state をそのまま付けてアプリに戻す
            3. アプリは、戻ってきた値が保存した値と一致するか確認する。一致しなければ処理を止める
            4. 照合が終わったら、その state は捨てる（使い回させない）

            入れてはいけない値

            • 1, 2, 3…（連番）— 次の値を推測できる
            • 現在時刻 — だいたいの値を推測できる
            • メールアドレスなど — 推測でき、個人情報がURLやログに残る
            • login のような毎回同じ固定値 — 使い回せるので照合の意味がなくなる

            目安は、安全な乱数で作った32バイト（256ビット）の値を、URLに使える文字列（Base64URL）にしたものです。ログインのたびに新しい値を作ります。

            用語ミニ解説

            アニメーションに出てきた言葉だけに絞っています。

            クライアント Client

            あなたのデータを使いたいアプリ側。記事の言葉では「ログインしたいサービス」。OAuthでは「許可をもらう側」です。

            認可サーバー Authorization Server

            ログインと同意を受け付け、トークンを発行するサーバー。Googleや社内SSO基盤。OIDCではOpenIDプロバイダー（OP）と呼ばれます。

            リソースサーバー Resource Server / API

            データを持つサーバー。アクセストークンの宛先で、トークンのscopeを見て「どこまで返してよいか」を判断します。

            scope scope=photos.readonly

            許可の範囲の宣言。「写真の閲覧だけ」のように、アプリがどこまでできるかを決めます。同意画面で確認するのがこの範囲です。

            redirect_uri

            認可後に戻るURL。認可サーバーに事前登録したものと完全一致しないと拒否されます（オープンリダイレクタ防止）。

            認可コード code

            トークンへの引換券。ブラウザ経由でアプリへ届く。短命・使い捨てで、それ自体ではデータにアクセスできません。

            PKCE code_verifier / challenge

            verifierのハッシュがchallenge。開始時はchallengeだけを送り、引き換え時にverifier本体を見せて照合します。

            state

            ログイン開始時に作るランダムな値。戻ってきたときに照合して、CSRF（別のログイン結果の送りつけ）を防ぎます。

            nonce

            OIDCで使う値。IDトークンの中に戻ってきて、古いIDトークンの使い回し（リプレイ）を防ぎます。stateと似ていますが、確認する場所が違います。

            OIDC（認証）とのつながり

            このページのフローに scope=openid を足し、IDトークンの受け渡しを加えたものがOIDCです。

            • OAuth：アプリ ⇔ 認可サーバー ⇔ API の間の「許可の取り決め」
            • OIDC：その許可のやり取りに「ログインしたのは誰か」を標準の形で載せたもの
            • 「Googleでログイン」の裏側では、認可（OAuth）と認証（OIDC）が同時に走っています

            やってはいけないこと

            • Implicitフロー（トークンをURLで直接返す旧方式）を新規採用する
            • IDトークンをAPIのアクセストークン代わりに使う
            • PKCEなしの認可コードフローにする（コード横取りに弱くなる）
            • stateの照合を省略する（ログインCSRFが成立する）
            • アクセストークンをlocalStorageに無造作に置く（XSSで盗まれる）
            • redirect_uriをワイルドカードで広く登録する
