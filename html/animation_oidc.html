OIDCの仕組み — 「Googleでログイン」のような仕組みは何をしているのか

OpenID Connect（OIDC）は、OAuth 2.0の上に「本人確認」を載せた仕組みです。パスワードをサービスごとに渡さず、IdP（Googleなど）が発行する IDトークン で「誰か」を証明します。下のアニメーションで、認可コードフロー＋PKCEを1ステップずつ追ってみましょう。

概要

OIDC（OpenID Connect）は、OAuth 2.0の上に「本人確認」を標準の形で載せた仕組みで、「Googleでログイン」のような機能の正体です。

サービスごとにパスワードを預ける形では、漏洩の危険も管理の負担もサービス数だけ増えていくため、本人確認を専門のIdPに任せる形が求められました。

サービスはIdPが署名したIDトークンを受け取るだけで「誰がログインしたか」を確かめられ、パスワードを一切扱わずにログイン機能を持てます。

背景

OIDCが生まれた背景 — 本人確認を自前で抱える限界

サービスの数だけパスワードが増えた

Webサービスが増えるにつれ、利用者はサービスごとにIDとパスワードを作ってきました。作る側も、パスワードの保管や漏洩時の対応、再設定の仕組みまで自前で抱えることになります。本人確認はどのサービスにも必要なのに、実装と責任がサービスごとに重複している状態でした。

企業の中でも似た問題がありました。社内システムが増えるたびにログイン先が増え、利用者は何度も認証し直し、管理側はアカウントの棚卸しをシステムごとに繰り返します。「本人確認を1か所に集約したい」という需要は、コンシューマー向けサービスと社内システムの両方にありました。

OAuthだけでは「誰か」が伝わらなかった

OAuth 2.0によって「パスワードを渡さずにAPIアクセスを許可する」形は整いました。しかしOAuthが渡すアクセストークンは「データへのアクセス許可」であり、「今ログインしているのが誰か」を標準の形で伝える決まりはありませんでした。各サービスがアクセストークンやプロフィール取得のAPIをログインの代わりに使ううちに、宛先の違うトークンを取り違えるといった事故も起きやすくなりました。

たとえば、あるサービス向けに発行されたアクセストークンを別のサービスへ提示し、そのままログインできてしまうような取り違えです。トークンの宛先や発行者を確認する手順が標準として決まっていないと、実装する側は正しさを自分で定義するしかありませんでした。

ないとどうなるか

OIDCがなければ、「ソーシャルログイン」は今もサービスごとの独自実装の寄せ集めだったはずです。本人確認の結果をどう受け取り、どう検証するかという決まりがなければ、安全性は実装ごとにばらつきます。IDトークンという署名付きの標準形式と、その検証手順を用意したことで、「本人確認はIdPに任せ、サービスは検証に徹する」という分業が成り立つようになりました。

標準化の副産物として、検証を肩代わりするライブラリや認証基盤の製品が揃いました。小さなサービスでも、大手IdPと安全に連携する土台を持てるようになったのは、この取り決めが先にあったからです。

          読み物

          仕組みを文章で読む — 認可コードフロー＋PKCE

          アニメーションを再生しなくても追えるよう、メインの認可コードフロー（11ステップ）を文章でもたどっておきます。

          往路：ブラウザがIdPへ運ぶ

          あなたがサービスのログイン画面で「IdPでログイン」のボタンを押すと、サービス（RP）はログインの準備を始めます。使い捨ての秘密である code_verifier を作って、そのハッシュである code_challenge を用意し、あわせて state と nonce という乱数を生成して、あなたのブラウザのセッションに保存します。verifier本体はRPの中に残り、外に出るのはハッシュ化されたchallengeだけです。

          ブラウザはIdPの認可endpointへリダイレクトされます。URLには client_id や redirect_uri、scope=openid、state、nonce、code_challenge が載ります。アドレスバーに載る情報は漏れる前提なので、秘密はここに含まれません。IdPの画面であなたが本人確認と同意を終えると、IdPは認可コードを発行し、登録済みの redirect_uri へブラウザを戻します。コードと一緒に、送ったときと同じ state が返ってきます。

          復路：サーバー同士の直接通信

          コードを受け取ったRPは、まず state が保存した値と一致するかを確認します。一致しなければ、そのログインは自分が仕掛けたものではないとして中断します。問題なければ、RPのサーバーがIdPのトークンendpointへ直接HTTPSで通信し、コードと code_verifier、client_secret を提示して引き換えを要求します。このサーバー間の直接通信がバックチャネルで、ブラウザは経由しません。

          IdPは verifier のハッシュが認可時の challenge と一致することを確かめ、問題なければ署名付きのIDトークンとアクセストークンを発行します。コードを盗んだだけの攻撃者は verifier を持たないため、この引き換えは成立しません。

          検証：IDトークンを信じる前に

          RPはIDトークンを受け取って終わりではありません。IdPの設定情報は Discovery で、公開鍵は JWKS で取得しておき、署名を公開鍵で検証します。さらに iss が想定したIdPか、aud が自分の client_id か、有効期限が切れていないか、nonce が開始時の値と一致するかをすべて確認し、1つでも失敗すればログインを拒否します。全部を通って初めて、RPは自前のセッションを作ってログインを完了させます。

          なお、名前やメールアドレスなどの追加情報が必要な場合は、アクセストークンを使って UserInfo endpoint から取得します。IDトークンはあくまで本人確認の結果であり、プロフィール全体を運ぶ手段ではない、という役割分担です。

          IDトークン（JWT）の中身

          色のついた3つの部分をタップすると、役割が分かります。IDトークンは「暗号化」ではなく「署名付き」— 中身は誰でも読めるので、秘密を入れてはいけません。

          ..
          ヘッダー（赤） — 署名アルゴリズム alg=RS256 と、鍵のID kid。RPはこのkidでJWKSから公開鍵を選びます。alg はRP側で固定し、ヘッダーの値をそのまま信用しません。

          ペイロードの代表クレーム

          • iss 発行者（IdPのURL）— 想定したIdPか？
          • aud 宛先（自分の client_id）— 他サービス向けトークンの流用防止
          • sub ユーザーの恒久ID（メールアドレスではない）
          • exp / iat 有効期限 / 発行時刻
          • nonce RPが送った値と一致するか — リプレイ防止
          • email / name / picture scopeで許されたプロフィール

          RPが必ずやる検証（全部）

          • 署名アルゴリズムをRP側で固定する（ヘッダーの alg をそのまま信用しない）
          • 署名をJWKSの公開鍵で検証する
          • iss が設定したIdPと一致する
          • aud に自分の client_id が含まれる
          • exp が切れていない
          • nonce がログイン開始時に保存した値と一致する

          1つでも失敗したらログイン拒否。「署名が合う＝中身が改ざんされていない」ことの証明です。

          OAuth 2.0 と OIDC の違い

          OAuth 2.0OIDC
          目的認可 —「何をしてよいか」
          APIアクセスの委任          		認証 —「誰か」を伝える
          （OAuth 2.0の上に載せた本人確認の層。APIの認可はOAuthの部分で行う）
          成果物アクセストークンIDトークン ＋ アクセストークン
          ユーザー情報仕様にない（独自実装）標準クレーム / UserInfo endpoint
          例えホテルのキーカード（部屋に入れる）キーカード＋身分証（誰のカードか分かる）

          だから「OAuthでログイン」は厳密には誤りで、正しくは「OIDCでログイン、OAuthでAPI認可」です。

          なぜコードを直接トークンにしないの？

          • 認可コードはブラウザを経由するため、履歴・ログ・悪性拡張機能に漏れる前提で設計する。だから短命（通常10分以内）・1回限り。
          • トークン交換はバックチャネル（RPサーバー⇔IdPの直接HTTPS）で行い、ブラウザを経由しない。
          • PKCE：コードを横取りされても、RPだけが持つ code_verifier がなければ交換できない。
          • state は戻り先URLで照合してログインCSRFを防ぎ、nonce はIDトークンの中で照合してリプレイを防ぎます。OIDCではnonceもCSRF対策になり、PKCEもCSRF対策を兼ねます。役割は重なりますが、3つを併用するのが実装の取り違えにも強く安全です。

          用語ミニ解説

          アニメーションに出てきた言葉だけに絞っています。

          RP / Client Relying Party

          ログイン機能を使いたいサービス側。「IdPを信頼する側」だからRelying Party。記事では「アプリ（クライアント）」と呼んでいます。

          IdP / OP OpenID Provider

          本人確認とトークン発行を行う側。Google、Microsoft Entra ID、Auth0、Keycloakなど。OAuthでは「認可サーバー」と呼び、記事ではこの呼び方を使っています。

          scope openid profile email

          何を求めるかの宣言。openid が必須で、これがあるとOIDCとして動作する。

          redirect_uri

          認可後に戻るURL。IdPに事前登録したものと完全一致しないと拒否される（オープンリダイレクタ防止）。

          認可コード code

          トークンへの引換券。短命・使い捨て。ブラウザ経由でRPへ届く。

          PKCE code_verifier / challenge

          verifierのハッシュがchallenge。認可時はchallenge、交換時はverifierを提示し、IdPが照合する。

          Discovery /.well-known/openid-configuration

          IdPの設定一式（各endpointや対応方式）を置く標準URL。RPは手打ち設定を減らせる。

          JWKS jwks_uri

          IdPの公開鍵セット。鍵ローテーション時はここが更新され、RPはkidで鍵を選ぶ。

          UserInfo /userinfo

          アクセストークンで叩くと、許された範囲のユーザー情報を返すendpoint。IDトークンを補う。

          パスキーとの関係

          競合ではなく、階層が違う技術です。OIDCのステップ5「IdPでの本人確認」の中身として、パスワードの代わりにパスキー（WebAuthn）が使われることが増えています。

          • OIDC：サービス ⇔ IdP の間の「信頼の取り決め」
          • パスキー：あなた ⇔ IdP の間の「本人確認の手段」
          • つまり「Googleでログイン（OIDC）」のGoogle側ログインがパスキー、という組み合わせが今の主流形です。

          やってはいけないこと

          • Implicitフロー（トークンをURLフラグメントで直接返す旧方式）を新規採用する
          • IDトークンをAPIのアクセストークン代わりに使う
          • 署名検証をせずペイロードだけ読んでログインさせる
          • アクセストークンをlocalStorageに無造作に置く（XSSで盗まれる）
          • redirect_uriをワイルドカードで広く登録する
          強みと弱み

          OIDCの良い点と弱点

          良い点：本人確認を分業できる

          サービスはパスワードを保管しなくてよくなり、漏洩時の大きな火種を持たずに済みます。利用者も、覚えるパスワードの数を減らせます。本人確認の結果が署名付きの標準形式で届き、検証の手順まで決まっているため、実装ごとのばらつきは小さくなります。大手IdPの多要素認証や異常検知といった安全策の恩恵を、そのまま自サービスに持ち込める点も見逃せません。

          利用者の体験の面でも、一度IdPにログインしていれば、別のサービスへのログインがほぼそのまま通るシングルサインオンが実現します。サービスを渡り歩くたびに認証し直す手間がなくなります。

          弱点：IdPへの依存と検証の手間

          逆に、ログインの成否はIdPの稼働に左右されます。IdP側で障害が起きれば、自サービスが無事でもログインできません。また、IdPのアカウント自体が乗っ取られれば、それに紐づく複数サービスへ影響が広がります。集約は利便性と同時に、攻撃者にとっての狙いどころの集約でもあるのです。検証の項目も多く、署名やnonceの確認を省くような実装をすれば、OIDCの安全性は簡単に崩れます。安全に使うには、実績のあるライブラリに任せることが前提になります。

          弱点：伝わる情報の範囲の設計

          IdPから渡されるプロフィール情報は scope で制御されますが、何を要求し、何を保存するかはサービス側の設計次第です。必要以上に情報を集めれば、それはそのまま漏洩時の被害範囲になります。便利さと最小化のバランスは、仕組みではなく運用で決まります。

          まとめ

          まとめ

          OIDCは、OAuth 2.0の認可の流れに「誰がログインしたか」を伝える標準の層を足した仕組みです。サービスはパスワードを扱わず、IdPが署名したIDトークンを検証するだけで本人確認を終えられます。その代わり、安全性は検証を省略しないことに懸かっており、IdPへの依存も生まれます。「本人確認は専門の側に任せ、自分は検証に徹する」という分業の形こそが、OIDCの本質です。次にIdP連携を実装するときは、フローの見た目よりも先に、検証項目がすべて実装されているかを確認してください。
